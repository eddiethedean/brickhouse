# ADR 0017: Refine phase 0.1 delivery and evidence gates

- Status: accepted for planning; implementation tasks retain their actual state
- Date: 2026-10-20
- Planning task: B044
- Refines: ADR 0003 and ADR 0016

## Context

The owner requested another refinement of phase 0.1 after adding serverless/classic compute requirements. The existing code has persistent catalog/Delta foundations and a child-launch primitive. The Sparkless hooks recorded by B009 are Rust-only; B010.1 cannot use them from Python. The released SQL connector's local transport also needs an early feasibility decision. Neither risk should first surface during release assembly.

Some new compute children mix provider completion with verification performed by their consumers. In particular, B011.5 asks for query/connector results before its downstream statement work, and B017.4 asks for interruption cleanup owned by downstream B017.3. B014.4 also references later worker checks without a distinct completion boundary. B020.4 combines Terraform resource qualification and bundle workload qualification in one task.

## Decision

1. Preserve all existing parent acceptance criteria, release scope and completed evidence. Keep the initial release at **0.1.0**, including both bounded compute modes and the three warehouse types.
2. Add B045 as an early, bounded local SQL connector transport research task. It records exact client/TLS/auth/request behavior and a feasible/blocked decision; it cannot establish SQL execution support. B021 still requires actual query results and its original prerequisites.
3. Add B046, decomposed into Python provider contract research, upstream binding implementation, and a source/wheel/provider probe. B010 and its children explicitly depend on B046. A tested development wheel can unblock integration; B023 still requires a publicly available compatible artifact before release. No publishing authorization is implied.
4. Keep B011.5/B014.4/B017.4 focused on their resource or context deliverable. Add B011.6 for real warehouse admission/execution binding, B014.6 for compute/worker lifetime integration, and B017.5 for compute interruption with real kernels. B020.4 qualifies Terraform resources; B020.5 qualifies both bundle workload variants. Preserve the original parent criteria and map the full moved behavior to required children.
5. Make document 16 the operational release contract: current work lanes, exact fixture variants, finite case families, selected local limits, evidence ownership and stop conditions. These are local test/release targets, not newly verified Databricks defaults or configuration accepted by current code.

At this decision, the ledger had 46 work packages and 80 required phase 0.1 children. The original 73 children remain; the added seven are four integration/client tasks and three B046 children. A later five-task decomposition of B014.3 brings the current phase 0.1 total to 85; see [document 16](../plan/16-phase-0.1-initial-release.md). B043/B044/B045 are standalone research/planning tasks assigned to phase 0.1.

## Completion boundaries

A provider child passes its own real repository/state/API tests and publishes a usable contract. Its integration consumer proves actual execution, cancellation and data persistence. Both are required for parent completion. Moving a check to the consumer does not remove it or count a provider's simulated lifecycle as a successful workload.

The existing active implementation B013.2 and all previous task/capability states and evidence remain authoritative. B044 can complete on planning consistency checks. B045 and B046 remain planned; B010.1 remains blocked until the Python binding exists. Source inspection, synthetic transport failure, or this refinement cannot promote a runtime capability.

## Consequences

Independent work can resolve connector feasibility and the Python binding while worker supervision progresses. The final scope freeze stays in B023; document 16 supplies a bounded implementation contract now. Installation remains one distribution: the current dependency-free bootstrap is not the intended 0.1 core execution stack, and notebooks remain an optional extra with a required separate workflow gate.

There is no runtime/config/workspace migration, cloud request, credential read, upstream change or publication in this planning slice. See [the refined release contract](../plan/16-phase-0.1-initial-release.md) and [B044 evidence](../../artifacts/conformance/B044-phase-0.1-refinement.md).
