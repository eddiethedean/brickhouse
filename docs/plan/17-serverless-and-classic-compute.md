# 17 — Serverless and classic compute emulation

Research date: **2026-10-20**. Status: adopted implementation plan. B018 verifies selected local script and notebook workloads across seven serverless/classic compute selectors and reads a job-produced Delta commit through all three local SQL warehouse profiles. **Serverless/classic workload compatibility remains partial:** compute allocation is simulated, and broader runtime, access, environment, SQL, and Databricks service behavior remain unverified. B043 records the research; B019.1 now owns the bounded SQL/type/error and mode-specific fixture corpus. [ADR 0016](../decisions/0016-serverless-and-classic-compute-profiles.md) records the decision.

## Product commitment and terminology

BrickHouse will emulate observable **serverless and classic compute behavior** for Python jobs and notebooks, and **serverless, pro, and classic SQL warehouses**. Supported operations must execute real local code and read/write real shared tables. Compute IDs, node allocation, and infrastructure lifecycle are explicitly simulated. A successful resource-creation response alone cannot establish workload compatibility.

Track four independent choices: compute mode, access mode, environment/runtime reference, and client protocol. Databricks classic compute includes all-purpose and jobs compute; classic SQL warehouses are a different product. Classic compute does not imply Spark Classic APIs: recent standard-access runtimes also use Spark Connect. [Databricks compares these execution semantics](https://docs.databricks.com/aws/en/spark/connect-vs-classic), including analysis timing and temporary-view binding.

## Behavior contracts

Profile names below are proposed local contracts. They are distinct from `spark35-local-v1`, which remains an engine semantics target. A tested claim must name the exact combination of compute profile, Sparkless/provider/client versions, and reference runtime or serverless environment version. Do not infer compatibility for every combination or map an arbitrary Databricks Runtime string to Sparkless 3.5.

| Workload | Local behavior to implement | Explicit simulation or limitation |
|---|---|---|
| Serverless Python jobs/notebooks (`serverless-local-v1`) | Resolve the supported no-classic-cluster submission shape and environment; apply the selected configuration allowlist and ANSI/UTC defaults; execute real Python/DataFrame work; preserve isolated session state and accurate outputs/errors. | Infrastructure allocation and performance mode are simulated. Full Connect wire compatibility is a later gate. Unimplemented semantic differences remain individually unsupported. |
| Classic all-purpose/jobs (`classic-standard-local-v1`, `classic-dedicated-local-v1`) | Resolve new, existing, and shared job compute; validate runtime mapping and access mode; persist resource identity; execute real Python work with notebook attachment/reset and run-scoped job lifetimes. | Node types/counts and VM scaling are simulated. Fresh processes per job attempt intentionally exclude shared driver/module/singleton state; report the classic profile as partial for such workloads. |
| SQL (`sql-serverless-local-v1`, `sql-pro-local-v1`, `sql-classic-local-v1`) | Resolve a real local warehouse record; validate type/flags/settings; start/admit/execute/cancel statements through the shared SQL/table services; preserve schema/results and commit versions. | Infrastructure sizing and cloud autoscaling are simulated. Actual local admission limits must be enforced; Photon, predictive I/O and proprietary workload-management performance are not claimed. |

### Selection and validation

Normalize supported wire requests into immutable domain context before dispatch. Record compute profile, resource reference, access mode, selected environment, semantic settings and effective limits on the attempt/session. Do not add a fictitious `compute_mode` field to Databricks SDK requests; any BrickHouse-specific override belongs to its explicit local API/configuration contract.

For classic jobs, resolve `new_cluster`, `existing_cluster_id`, and `job_cluster_key` referencing a declared classic `new_cluster`. For initial serverless Python tasks, omit classic cluster selection and resolve `environment_key` against the job's environments. Notebook environment inheritance and job-level overrides require separate cases. Validate conflicting selectors, duplicate/missing keys, missing/deleted resources, unsupported runtime/access modes and invalid task/resource combinations before starting a worker. The SDK also has serverless compute-object selectors; phase 0.1 rejects those explicitly until their separate authorization/lifecycle contract is implemented in phase 0.2.

Match selected `Environment.client`/`environment_version` request forms to the pinned client's fixtures; reject conflicting or unmapped versions. Phase 0.1 resolves only explicitly provisioned local environments and verified dependencies. Requested package installation, init scripts, unknown dependencies or unsupported configuration must fail before dispatch. Phase 0.2 adds locked environment creation/cache/reset and the selected classic dependency modes. Never install arbitrary cluster libraries during a job or introduce a JVM package implicitly.

Serverless config rejection, lack of RDD/SparkContext/JVM access, global temporary-view/cache restrictions, file/volume rules, and session defaults need separate positive/error cases. Classic standard and dedicated restrictions must be keyed to their selected reference runtime. An operation allowed by Databricks dedicated compute can still be unsupported by BrickHouse; the error and capability entry must identify that local limitation. Local process isolation is not a sandbox, and access-mode labels alone do not establish identity enforcement. Full compute ACL enforcement is gated by B028 in phase 0.2.

**Implemented local SQL/session profile cases (B019.1.7):** Sparkless 4.15.0 resolves the selected serverless ANSI/UTC defaults separately from explicit classic-standard and classic-dedicated settings on the `spark35-local-v1` alias. Tests cover same-name temporary-view isolation, configuration allowlist failures, and explicit rejection of global temporary views and SQL/DataFrame cache operations. Unknown-column SQL is eager in the local engine; deferred Connect analysis and Connect protocol behavior remain unsupported pending B036. The only retained Databricks reference is a prior serverless SQL literal capture; no classic or Python-workload parity is inferred. See [B019.1.7 evidence](../../artifacts/conformance/B019.1.7-sql-session-profiles.md).

### Lifecycle and execution

A workspace-scoped compute domain service owns cluster and warehouse records in the authoritative SQLite store. HTTP adapters and the scheduler use it; no second catalog, scheduler, or data store is introduced. B011.5 owns its warehouse slice and B014.4 its classic job/all-purpose slice, with shared contracts and migrations reviewed together. B014.5 resolves execution context; B014.2 consumes it for local Python script tasks, and B014.3.1 dispatches supported DAGs sequentially. B014.6 now reserves, starts, and releases classic worker consumers and observes active all-purpose resource generations so a restart or termination cancels and reaps the associated process group. B011.6 proves statement effects; B017.5 proves kernel interruption after the notebook primitives. [Document 16](16-phase-0.1-initial-release.md) defines those completion boundaries and the bounded release corpus. B020 qualifies clients against those services rather than becoming a prerequisite needed to implement them.

Persist selected SDK lifecycle states and legal transitions. An all-purpose resource survives job completion; a job resource is scoped to one run, starts for its first consumer, and terminates after its last consumer. Restart/termination must invalidate affected sessions and cancel/reap active workers according to the documented policy. Restarting infrastructure never deletes committed Delta tables. A warehouse's start/stop/auto-stop and statement admission must agree; unknown warehouse IDs cannot be silently ignored. Validate the pinned connector's warehouse HTTP path against the same resource identity. B045 confirmed that the kernel session-open request carries `warehouse_id` from its explicit HTTP path; the local 401 capture did not exercise a warehouse or statement.

**Implemented resource slice (B014.4):** metadata schema 7 stores classic all-purpose identities and new/shared job resources with a generation counter, planned/active/released consumers, and an append-only lifecycle event journal. The pinned SDK 0.153.0 cluster create/get/list/edit/start/restart/delete/permanent-delete routes operate against that store. A controlled clock drives idle termination. Starting a shared job resource activates its first consumer; it remains running while any planned consumer is unreleased and terminates when the last consumer releases. All-purpose identity remains after termination and explicit consumer autostart preserves its ID. Events fence old sessions after restart, start, edit, or termination. The route state message and C057 capability both label allocation as simulated. `spark35-local-v1` is a BrickHouse-local alias, not a Databricks Runtime string; no Runtime/access parity or security boundary is inferred.

**Implemented SQL warehouse resource slice (B011.5):** metadata schema 13 persists the three SDK warehouse types, settings, lifecycle generations, events, and statement admission leases through the workspace compute service. The actual pinned SDK 0.153.0 calls the local loopback API for create/get/list/edit/start/stop/delete; serverless is represented as `PRO` plus `enable_serverless_compute=true`, with `PRO` and `CLASSIC` remaining distinct profiles. The selected release limits are enforced locally (one active per warehouse, two active workspace-wide, eight queued per warehouse) with FIFO promotion. Stop, delete, edit-generation changes, and controlled-clock auto-stop invalidate queued leases; active leases retain capacity until their worker reaches a terminal outcome, while the generation change fences further admission/commit. Allocation and states are simulated. B011.5 does not itself execute SQL or apply a queue timeout and does not claim Databricks admission or scaling parity.

**Terraform consumer evidence (B020.4):** Terraform Core 1.16.6 with provider 1.137.0 applies, reads, updates, refreshes, and destroys a classic cluster and all three local warehouse profiles. The provider's cluster refresh asks for `filter_by.is_pinned=true` even when pinning is false; because pin/unpin is not implemented, the local response is an empty pinned-only list and reports the cluster as unpinned. Provider destroy calls permanent-delete directly, so the local route terminates active clusters before removing their metadata. An invalid classic/serverless combination is rejected without changing persisted state. The provider's read-only `odbc_params` field remains unavailable because there is no local ODBC listener; after an update this leaves only that computed field in a residual Terraform plan for each warehouse. No ODBC/JDBC endpoint or cloud resource is represented. See [B020.4 evidence](../../artifacts/conformance/B020.4-terraform-compute-warehouses.md).

**Bundle workload evidence (B020.5):** Databricks CLI 1.21.0 validates, deploys, runs, updates, redeploys, and destroys a serverless-local Python bundle plus a classic-standard notebook bundle. The Python worker appends two typed G2 rows to the shared Delta table; a notebook reads the exact snapshot and checks its emitted result. A pinned SDK statement reads the same rows through a Pro warehouse with local serverless enabled. Stable public job identity, immutable run history, rejected task/selector/resource requests, bundle file cleanup, and simulated classic-resource release are asserted. The local serverless fixture requires `disable_auto_optimization: true`. The CLI uses a synthetic identity/token and loopback server; no Databricks cloud runtime or allocation is represented. See [B020.5 evidence](../../artifacts/conformance/B020.5-cli-serverless-classic-bundles.md).

**Implemented SQL statement slice (B011.2/B011.6/B011.3):** metadata schema 15 persists the original SQL text, typed parameter values, namespace, state, typed JSON manifest/result and terminal errors. The pinned SDK submits, polls, and fetches the first inline JSON_ARRAY chunk from actual local Sparkless execution over registered Delta data. Each request acquires persistent admission for its warehouse identity; one active per warehouse, two active workspace-wide, and eight queued per warehouse are enforced with FIFO promotion. All three simulated SQL warehouse profiles execute against the same committed table. Stop or generation invalidation cancels queued work and requests cancellation of active work. Active leases remain held until Sparkless reports a terminal result; a generation change fences later commits. Committed mutations remain successful if cancellation arrives after the commit fence, and a process restart marks RUNNING work failed without replay. Results are capped at 10,000 rows/8 MiB. Named scalar parameters support NULL, STRING, BOOLEAN, integer widths, FLOAT/DOUBLE, DECIMAL(p,s), DATE, and TIMESTAMP; positional markers, unsupported types, and invalid bindings fail before statement creation. The Statement Execution API implements its default 10-second wait, immediate 0-second response, and 5–50-second hybrid wait with `CONTINUE`; when a wait expires, the persisted statement ID and actual state remain available while a managed continuation runs once. Explicit cancellation and `on_wait_timeout=CANCEL` use Sparkless 4.15.0's public cancellation handle and terminal cancellation error, with pre-action and commit fences. Connector 4.6.0 passes a kernel FAST session open/close case and one SEA-mode named-INT `INLINE`/`JSON_ARRAY` execution/fetch/result-close case against loopback TLS. B021.2.3 verifies SQL and metadata failures, synchronous cancellation, result/session close, and retention; canceled responses surface as `ProgrammingError: Invalid result format`, and `SHOW CATALOGS`/rollback remain explicitly unsupported. Kernel Arrow-stream execution, other metadata methods, Thrift, and remote Databricks behavior remain unqualified. See [B021.2.3 evidence](../../artifacts/conformance/B021.2.3-sql-connector-failures-retention.md). B011.4 adds result chunks and expiry. Evidence: [B011.2](../../artifacts/conformance/B011.2-sql-statement-api.md), [B011.3.1](../../artifacts/conformance/B011.3.1-sql-parameter-binding.md), [B011.3.2](../../artifacts/conformance/B011.3.2-sql-wait-timeout.md), [B011.3.3](../../artifacts/conformance/B011.3.3-sparkless-4.15.0-cancellation.md), [B011.6](../../artifacts/conformance/B011.6-sql-warehouse-statement-binding.md), [B021.2.2](../../artifacts/conformance/B021.2.2-sql-connector-inline-results.md), and [B021.2.3](../../artifacts/conformance/B021.2.3-sql-connector-failures-retention.md). The operation journal carries the selected table ID transaction and fingerprint metadata. **Implemented scheduler slice (B014.3.1):** jobs may contain up to ten validated Python tasks. The local dispatcher uses a stable topological order, records dependency-blocked tasks as skipped without creating attempts, continues independent tasks after a failure, and derives the terminal run result from persisted task outcomes. Dispatch is sequential and supports only `ALL_SUCCESS`; B014.3.2.1 adds bounded retries, B014.3.2.2 originally admitted four active local workers; B064 supersedes it with at most two active attempts and eight persisted FIFO queued runs, per-job `max_concurrent_runs` 1–10, stable reset identity, and safe restart recovery of undispatched work. B014.3.3 still interrupts runs with started attempts rather than replaying user code. A still-running orphan process is not adopted and may finish side effects before the interrupted state becomes visible.

Each job attempt still uses a fresh Python child; a notebook kernel retains its own state between cells and loses it on reset. Compute sharing never grants accidental cross-run/session access to config, UDFs, temporary views, imports, parameters or secrets. Preserve worker exit codes, failure categories, logs and committed write outcomes even when the surrounding infrastructure is simulated.

Use deterministic local clocks and explicit transition hooks for idle/start/stop tests; do not make tests sleep for cloud startup. Return actual measured local timings with simulation labels. Resource states are durable simulation; job/statement success requires actual execution and stored results. Requests for unsupplied cloud, network, GPU, policy or runtime effects require explicit unsupported responses.

### Analysis, retries and later domains

Serverless must eventually reproduce Connect-style analysis/error timing and temporary-view/UDF binding where advertised. The phase 0.1 local corpus does not establish those cases or a Connect server. Track delayed unknown-column errors and view replacement separately; B036 must prove them with an unmodified pure Python client in phase 0.7. Classic reference runtimes using Connect share that analysis profile; older Spark Classic behavior needs its own fixtures.

Distinguish submission idempotency, configured task retries, serverless automatic optimization retries, and interrupted-write reconciliation. Phase 0.1's serverless fixture explicitly disables automatic optimization retries using the pinned task field until B024 implements the selected bounded policy in phase 0.2. Unsupported retry settings fail explicitly. Every retry has a new attempt and consults the shared mutation journal; external Python side effects have no exactly-once guarantee. Performance targets may be recorded as simulated allocation settings, with no invented latency/DBU effects.

B030–B035 carry mode restrictions into streaming and pipelines: serverless bounded-trigger acceptance/rejection is a distinct corpus from classic triggers. Serverless model serving, GPU workloads, networking, Lakebase and other products remain separately tracked capabilities, not implied by serverless Python or SQL support.
