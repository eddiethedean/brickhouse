# 12 — Delivery, configuration, and operations

## Emulator-first deployment policy

Current implementation and phases 0.1–0.9 target the JVM-free local Databricks emulator. B048 and its children are complete: the code/evidence review and loopback-bind remediation are attached to the B023.1 scope inventory. They do not introduce network exposure, persistent deployed secrets, a container runtime or remote workers. All actual deployment implementation is behind B049's stability assessment after B042. [Document 18](18-self-hosted-platform.md) and [ADR 0034](../decisions/0034-emulator-first-self-hosted-platform.md) define SH.0–SH.6, proposed deployment profiles and future operations contracts.

SH.1 must provide authenticated encrypted ingress, consistent service policy, protected durable credentials, bounded admission and coordinated restore for trusted code authors. SH.3 adds a real tested code-isolation boundary; SH.4 adds enrolled remote workers and explicit artifact/native-storage transport while keeping a single metadata/commit authority. SH.5 qualifies install/upgrade, protected secret recovery/rotation, coordinated cross-host restore, measured recovery/capacity objectives, observability and operator runbooks. These are planned requirements, not current configuration or security guarantees. No HA, shared network SQLite or replacement database is assumed. The base local wheel must remain independent of this optional infrastructure.

## Workspace layout

Workspace-owned state lives outside the source checkout. The initial B006.1 implementation creates the listed directories and the versioned config/SQLite bootstrap; later services will own their contents.

```text
workspace/
  brickhouse.toml       # non-secret configuration and format version
  metadata.sqlite      # catalog/jobs/operation metadata
  .brickhouse-owner.lock # exclusive local service ownership
  tables/              # managed Delta directories keyed by stable IDs
  files/               # workspace source and local DBFS/volume roots; B016.1 maps DBFS to files/dbfs/
  staging/             # incomplete inputs and transient result batches
  results/             # bounded statement artifacts
  runs/                # attempt logs, manifests, notebook artifacts
  checkpoints/         # versioned streaming state when supported
  integrations/        # provider-owned state with explicit backup hooks
```

User-configured external table locations remain external. Credentials must not be serialized into run manifests or ordinary config. B016.2 currently provides an in-memory `WorkspaceContext.secret_provider`; embedding code configures values with `put(scope, key, value)` and grants an existing job with `grant_job(job_id, scope)`. The provider does not read `.env`, persist secret values/grants, or expose secret-management HTTP routes, so applications must configure it again after service restart. Worker values travel through a bounded attempt-local pipe and exact output values are redacted before persistence; transformed values cannot be reliably identified. This is trusted-machine process isolation, not encryption or a hostile-code boundary. Do not claim local tokens make arbitrary notebook execution safe.

## Configuration and lifecycle

Use a typed configuration model with precedence: explicit invocation arguments, designated environment variables, workspace config, defaults. Document the actual supported settings; reject invalid/unknown settings where silent acceptance would imply behavior. Separate compatibility profile from engine selection and client versions.

Implemented selected compute resolution follows [document 17](17-serverless-and-classic-compute.md): persist workspace compute/warehouse identity and immutable effective mode/access/environment/runtime settings per attempt/session. Reject unmapped environments or unsupported settings before dispatch. Resolve only provisioned environments in phase 0.1; phase 0.2's locked provisioning/cache/reset requires its own offline artifacts and conformance evidence. The selected SDK compute selectors and persisted attempt context are implemented; arbitrary environment installation and phase 0.2 configuration remain unsupported.

All unauthenticated diagnostics-server entry points accept numeric IPv4 loopback hosts only; the CLI and direct factory/serving APIs share validation before workspace acquisition or socket binding. This prevents accidental network exposure but does not authenticate callers or sandbox Python. One workspace has one active service owner, guarded by a lock with stale-owner recovery. Worker processes call that service for writes. Validate ownership and schema version before opening writable state. A second server must fail clearly rather than run competing migrations.

`initialize_workspace()` creates a new workspace with explicit bootstrap namespaces and refuses an existing target. `open_workspace()` reopens and validates a supported workspace through read-only metadata access. Workspace format version 1 uses `main.default` by default; the account-specific Databricks `workspace` catalog observed during reference capture does not define the local policy. Metadata schema version 21 includes catalog/schema IDs, comments, `information_schema`, table registrations, the per-table operation journal, durable worker outcomes with process identity and interrupted state, job/run/task/attempt state, simulated classic compute resources/consumers/lifecycle events, bounded stdout/stderr per job attempt with a one-way 24-hour expiry transition, run/task/attempt/key-scoped task values, append-only Terraform job revisions behind stable resource IDs, and immutable SDK job deletion tombstones. Invalid/unknown config, unsupported config or storage versions, mismatched defaults, corrupt metadata, and missing workspace directories fail explicitly. B006.2 adds `acquire_workspace_owner()` with a nonblocking POSIX advisory lock and a transactional SQLite migration runner. B006.3 composes the owner into `Workspace.local(directory)` and `brickhouse serve`, releasing it on normal exit, Ctrl-C, and SIGTERM. The embedded context exposes instance-scoped namespace/table metadata repositories, operation journaling, durable job state, classic compute lifecycle state, and fresh namespace state. The internal B010.1–B010.3 Sparkless factory uses those repositories and the optional Delta service to read registered version-pinned local tables, route selected managed/named/path writes through the journaled provider, and apply resolved serverless settings plus one explicit classic-standard local runtime to isolated coexisting sessions; it is not exposed through `Workspace.session()`. Job workers separately receive the selected worker-scoped Sparkless session and registered-table DeltaTable read facade. `serve` requires an existing workspace and provides loopback health/version/capability, catalog/schema routes, classic cluster lifecycle routes, Python source import, the pinned-SDK Python job create/submit/status/output/delete subset, and the pinned Terraform workspace-file/single-task job lifecycle subset. The Databricks CLI v1.21.0 bundle profile additionally uses a simulated current-user identity, workspace file status/import/export/directory/delete routes, and the same single-task Python job API to validate, deploy, run and destroy one classic bundle fixture. Bundle destruction deletes the fixture's managed workspace tree and tombstones the job while retaining its immutable definition and run history. The Terraform host-discovery identity is simulated and only scopes the local provider route profile; neither profile authenticates callers. Jobs run in fresh local Python processes; broad Databricks runtime and infrastructure allocation are not emulated. B014.6 reserves/starts/releases each classic worker's compute consumer, keeps all-purpose identity persistent, and cancels/reaps a live worker when its selected all-purpose generation changes or resource terminates. At startup and while polling, B014.3.3 reconciles a run after its recorded worker PID is gone, preserves prior terminal output, marks unobserved in-flight attempts interrupted with no exit code or automatic replay, and releases that run's compute consumers. A surviving orphan worker is not adopted; its run remains active until the worker exits and a later poll can reconcile it. B013 supplies worker supervision, B014.1 durable job state, B014.2 the current SDK worker flow, B014.4 simulated compute lifecycle metadata, B014.5 pre-dispatch selector/environment resolution, and B014.6 worker/resource integration. `brickhouse run` still explicitly fails; its direct-script lifecycle has not been composed. A dead server releases the kernel lock; stale PID data does not prevent recovery. POSIX local filesystems are the tested scope; Windows and network filesystems are not claimed. Metadata schemas 1–21 upgrade transactionally under workspace ownership; schema 20 adds worker-output expiry and schema 21 adds stable job admission keys plus durable dispatch markers for FIFO queue recovery. The workspace format remains version 1. Output retrieval performs a lazy expiry sweep and reports `logs_expired`; no background expiry scheduler is implemented. Workspace format version 1 remains unchanged.

B020.4 adds a selected Terraform resource profile over the same local metadata service: one simulated classic cluster and serverless/Pro/classic warehouses. Provider destroy can permanently remove an active cluster, which the API handles by recording termination before metadata removal. SQL warehouse resources intentionally omit computed `odbc_params`: no ODBC listener exists, and Terraform retains a computed-field-only plan after updates. See the [B020.4 conformance report](../../artifacts/conformance/B020.4-terraform-compute-warehouses.md) for the exact provider pin and boundary.

B020.5 validates and runs selected CLI bundles against the local job service: a serverless-local Python bundle writes G2 rows to the shared Delta table, is updated and redeployed under a stable job ID, and a classic-standard notebook bundle reads those rows with checked output. A pinned SDK statement reads the same table through the local Pro/serverless-enabled warehouse profile. Invalid task/selector/resource requests and cleanup are covered. The local Python mapping, synthetic identity, cluster and warehouse lifecycle remain local/simulated; `disable_auto_optimization: true` is required for the serverless fixture. See the [B020.5 conformance report](../../artifacts/conformance/B020.5-cli-serverless-classic-bundles.md). No Databricks cloud compatibility is implied.

All processes must propagate cancellation and exit status. Terminate descendant process groups after a configurable grace period; avoid orphan kernels. Bound queue length, concurrent jobs, query results, logs, and staged files. Reject overloaded requests with a documented error rather than exhausting the host.

B013.1 adds the internal `run_python_worker()` launch primitive: resolved absolute interpreter/script paths, explicit cwd, size-limited immutable JSON context, a minimal environment, concurrent bounded stdout/stderr capture, and the real child exit code. B013.2 adds versioned private worker messages and attempt-scoped bearer authentication. B013.3 adds timeout/cancellation, POSIX process-group escalation, attempt-token revocation, safe staging cleanup callbacks, and SQLite worker outcome records. B014.1 adds immutable job definitions/submissions, task snapshots, validated DAG metadata, distinct attempt identities and accurate state persistence. B014.2 composes pinned-SDK workspace source import, single-task Python dispatch, status polling, and bounded persisted output. B014.3.1 adds sequential DAG dispatch with persisted dependency-failure skips; B014.3.2.1 implements bounded per-task retry attempts; B014.3.2.2 implements run concurrency admission; B014.3.3 reconciles active runs after restart. B014.4 adds simulated cluster identity/lifecycle, run-scoped consumer tracking and generation-based invalidation in metadata schema 7; B014.5 resolves selected execution context; B014.6 binds all seven selected job variants to worker consumers and cancels/reaps active workers on all-purpose compute invalidation. Job workers receive a selected Sparkless session plus registered-table DeltaTable reads. Authenticated DataFrame append to existing registered tables routes through the parent table service; worker table creation, overwrite and arbitrary path writes remain unsupported.

## Persistence and recovery

SQLite migrations are versioned and transactional where supported. Refuse to open a newer workspace format with an older binary. Test upgrades from supported prior versions; define backup requirements before destructive migrations. SQLite WAL and filesystem locking assumptions must be documented; network filesystems are unsupported until tested.

Use an operation journal for transitions spanning metadata and Delta/files. B008.3 implements local Delta intent, a payload/options fingerprint, per-table monotonic transaction version, and final commit version in SQLite schema 4. Before replay, it requires the matching provider transaction version and exact operation/fingerprint entry in recent Delta history; a confirmed transaction without its exact history version is insufficient. Known committed replays return the original version, changed-payload operation-key reuse fails, and unconfirmed outcomes block further writes for that table until the same operation is reconciled. History lookup is bounded to 100 recent commits; expired or unavailable evidence stays uncertain. B022.1 verifies real POSIX process death before Delta dispatch, after Delta commit but before SQLite finalization, and after SQLite finalization; reopen either preserves uncertainty or reconciles the exact committed version without a duplicate. B022.2 verifies same-process serialization for concurrent SQL MERGE and Sparkless DataFrame appends issued through distinct workspace catalogs and canonical path aliases. The SQL path's stale snapshot is rejected before journal preparation, then a caller retry with the same operation ID commits once; both operations replay their original versions. This proves in-process location locking only, not cross-process or cross-host coordination. B008.4 deletes a managed table's files before its registration, so interrupted recursive cleanup can be retried from the still-present registration; external drop removes only metadata. The table's operation rows are pruned atomically with registration removal. B022.3.1 confirms the staged Parquet input is retained while an operation is uncertain and can be deleted after exact commit reconciliation; same-payload replay returns the recorded version and changed-payload reuse is rejected after restart. Worker attempt logs expire after 24 hours on output retrieval or explicit maintenance; result chunks expire after 12 hours while SQL statement metadata remains. B022.4 confirms a serverless-local task that times out after committing a Delta append is recorded as timed out, its worker is reaped, and the committed version is not automatically replayed after reopening; an explicit retry after a pre-commit failure uses a distinct attempt and creates one commit. Classic compute restart/termination and notebook interruption preserve earlier commits in B018.1.2 and B017.5. This local recovery path does not cover external Python side effects, cross-process coordination or remote service semantics. Avoid blindly rerunning a job whose external effects cannot be reconciled. See [B022.1 evidence](../../artifacts/conformance/B022.1-commit-boundary-crashes.md), [B022.2 evidence](../../artifacts/conformance/B022.2-concurrent-alias-writes.md), and [B022.4 evidence](../../artifacts/conformance/B022.4-serverless-timeout-commit.md).

Back up a quiesced workspace or use a coordinated snapshot procedure that captures consistent SQLite, Delta logs/data, and provider state. Copying a live SQLite main file alone is not a backup. External tables need a manifest and an explicit inclusion policy; do not delete or duplicate them as an incidental backup action. Restore tests must read real data and job history. B022.3.2 implements `brickhouse.workspace.snapshot_workspace()` and `restore_workspace_snapshot()` for a local closed/quiesced workspace: the owner lock excludes BrickHouse writers, unfinished Delta/job/SQL records reject capture, SQLite WAL is checkpointed when enabled, symbolic links are rejected, and a sidecar manifest records the excluded external-table references. Restore requires a new disjoint path, validates the snapshot v2 managed-table inventory against copied file trees even if the source workspace is unavailable, rebases managed registrations to the restored `tables/<table_id>` directories, and preserves external absolute locations without copying their bytes. Truly unmaterialized managed registrations remain valid; missing or changed materialized data fails restore. A missing external location remains registered and Delta reads fail explicitly with `TableMissingError`. External writers are not coordinated, external provider state is not captured, and a restored clone sharing external tables must not be concurrently mutated with its source.

## Observability

Structured events include workspace, request, job/run/task/attempt, statement, table, operation, and Delta version IDs as applicable. Preserve user stdout/stderr separately from service events. Redact known secrets and avoid logging SQL parameter values by default; redaction cannot guarantee arbitrary user code will never reveal secrets.

The server exposes local health, package version, capability reports, catalog/schema REST routes, classic cluster lifecycle routes, Python workspace-file import and the bounded Python job API. Provider detection uses package metadata only and does not import optional modules. B008.2 adds the explicit local `DeltaRsTableService`; B008.3 adds its durable operation journal and replay reconciliation, and B008.4 adds external deregistration and safe local managed cleanup. B010.1–B010.3 compose the service into the internal Sparkless session factory for selected local reads/writes and verify coexisting profile-bound session state; B011 and B018.1 use the same authority for SQL and bounded worker appends. The base package pins Sparkless, delta-rs, PyArrow, and SQLGlot. Notebook kernel dependencies remain in `brickhouse[notebooks]`. SDK behavior is tested against the pinned client on loopback and does not establish Databricks workspace compatibility. Report simulated cluster metadata clearly. Metrics include queue time, execution time, failure category, result bytes, and worker resource use where supported. Do not silently send telemetry outside the machine.

A bounded local capture verified the Free Edition workspace, used one existing serverless 2X-Small SQL warehouse for one synthetic statement, and returned it to its initial stopped state. The host and token are not stored in tracked configuration. There are no automatic push/PR/schedule triggers or required CI dependency. Normal tests and runtime must not load `.env` or inherit real-workspace authentication. The GitHub workflow has not been dispatched; secret/variable availability and artifact upload remain unverified.

The qualified release targets are Ubuntu 22.04 x86_64 and macOS 26 arm64 on Python 3.11/3.12; exact measured interpreter/image versions and artifact hashes are in the release bundle. macOS 14 remains unqualified after intermittent native CLI sandbox failures. Test Windows and additional architectures before advertising them. Do not force users to install a Rust compiler to compensate for an untested wheel matrix.

The selected local fixture limits and overload/expiry/cancellation assertions are specified in [document 16](16-phase-0.1-initial-release.md#local-fixture-limits-and-overload-behavior). ## Supply chain boundary

Pin copied source provenance and audit intentional private-API use. Validate optional native/service artifacts independently. Separate local development dependency overrides from public install requirements. Environment creation for jobs must use an explicit dependency manifest and provisioning policy; arbitrary job-time package installation is unsupported initially.
