# 12 — Delivery, configuration, and operations

## Emulator-first deployment policy

Current implementation and phases 0.1–0.9 target the JVM-free local Databricks emulator. B048 reviews existing code and G1–G4 before B023; it does not introduce network exposure, persistent deployed secrets, a container runtime or remote workers. All actual deployment implementation is behind B049's stability assessment after B042. [Document 18](18-self-hosted-platform.md) and [ADR 0034](../decisions/0034-emulator-first-self-hosted-platform.md) define SH.0–SH.6, proposed deployment profiles and future operations contracts.

SH.1 must provide authenticated encrypted ingress, consistent service policy, protected durable credentials, bounded admission and coordinated restore for trusted code authors. SH.3 adds a real tested code-isolation boundary; SH.4 adds enrolled remote workers and explicit artifact/native-storage transport while keeping a single metadata/commit authority. SH.5 qualifies install/upgrade, protected secret recovery/rotation, coordinated cross-host restore, measured recovery/capacity objectives, observability and operator runbooks. These are planned requirements, not current configuration or security guarantees. No HA, shared network SQLite or replacement database is assumed. The base local wheel must remain independent of this optional infrastructure.

## Workspace layout

Workspace-owned state lives outside the source checkout. The initial B006.1 implementation creates the listed directories and the versioned config/SQLite bootstrap; later services will own their contents.

```text
workspace/
  brickhouse.toml       # non-secret configuration and format version
  metadata.sqlite      # catalog/jobs/operation metadata
  .brickhouse-owner.lock # exclusive local service ownership
  tables/              # managed Delta directories keyed by stable IDs
  files/               # workspace source and local DBFS/volume roots; B016.1 maps DBFS to files/dbfs/
  staging/             # incomplete inputs and transient result batches
  results/             # bounded statement artifacts
  runs/                # attempt logs, manifests, notebook artifacts
  checkpoints/         # versioned streaming state when supported
  integrations/        # provider-owned state with explicit backup hooks
```

User-configured external table locations remain external. Credentials must not be serialized into run manifests or ordinary config. B016.2 currently provides an in-memory `WorkspaceContext.secret_provider`; embedding code configures values with `put(scope, key, value)` and grants an existing job with `grant_job(job_id, scope)`. The provider does not read `.env`, persist secret values/grants, or expose secret-management HTTP routes, so applications must configure it again after service restart. Worker values travel through a bounded attempt-local pipe and exact output values are redacted before persistence; transformed values cannot be reliably identified. This is trusted-machine process isolation, not encryption or a hostile-code boundary. Do not claim local tokens make arbitrary notebook execution safe.

## Configuration and lifecycle

Use a typed configuration model with precedence: explicit invocation arguments, designated environment variables, workspace config, defaults. Document the actual supported settings; reject invalid/unknown settings where silent acceptance would imply behavior. Separate compatibility profile from engine selection and client versions.

Planned compute selection follows [document 17](17-serverless-and-classic-compute.md): persist workspace compute/warehouse identity and immutable effective mode/access/environment/runtime settings per attempt/session. Reject unmapped environments or unsupported settings before dispatch. Resolve only provisioned environments in phase 0.1; phase 0.2's locked provisioning/cache/reset requires its own offline artifacts and conformance evidence. These are future configuration contracts, not settings currently accepted by `brickhouse.toml`.

Bind to loopback by default. One workspace has one active service owner, guarded by a lock with stale-owner recovery. Worker processes call that service for writes. Validate ownership and schema version before opening writable state. A second server must fail clearly rather than run competing migrations.

`initialize_workspace()` creates a new workspace with explicit bootstrap namespaces and refuses an existing target. `open_workspace()` reopens and validates a supported workspace through read-only metadata access. Workspace format version 1 uses `main.default` by default; the account-specific Databricks `workspace` catalog observed during reference capture does not define the local policy. Metadata schema version 12 includes catalog/schema IDs, comments, `information_schema`, table registrations, the per-table operation journal, durable worker outcomes with process identity and interrupted state, job/run/task/attempt state, simulated classic compute resources/consumers/lifecycle events, immutable bounded stdout/stderr per job attempt, run/task/attempt/key-scoped task values, append-only Terraform job revisions behind stable resource IDs, and immutable SDK job deletion tombstones. Invalid/unknown config, unsupported config or storage versions, mismatched defaults, corrupt metadata, and missing workspace directories fail explicitly. B006.2 adds `acquire_workspace_owner()` with a nonblocking POSIX advisory lock and a transactional SQLite migration runner. B006.3 composes the owner into `Workspace.local(directory)` and `brickhouse serve`, releasing it on normal exit, Ctrl-C, and SIGTERM. The embedded context exposes instance-scoped namespace/table metadata repositories, operation journaling, durable job state, classic compute lifecycle state, and fresh namespace state, but no Sparkless session or Delta data service. `serve` requires an existing workspace and provides loopback health/version/capability, catalog/schema routes, classic cluster lifecycle routes, Python source import, the pinned-SDK Python job create/submit/status/output/delete subset, and the pinned Terraform workspace-file/single-task job lifecycle subset. The Databricks CLI v1.21.0 bundle profile additionally uses a simulated current-user identity, workspace file status/import/export/directory/delete routes, and the same single-task Python job API to validate, deploy, run and destroy one classic bundle fixture. Bundle destruction deletes the fixture's managed workspace tree and tombstones the job while retaining its immutable definition and run history. The Terraform host-discovery identity is simulated and only scopes the local provider route profile; neither profile authenticates callers. Jobs run in fresh local Python processes; broad Databricks runtime and infrastructure allocation are not emulated. B014.6 reserves/starts/releases each classic worker's compute consumer, keeps all-purpose identity persistent, and cancels/reaps a live worker when its selected all-purpose generation changes or resource terminates. At startup and while polling, B014.3.3 reconciles a run after its recorded worker PID is gone, preserves prior terminal output, marks unobserved in-flight attempts interrupted with no exit code or automatic replay, and releases that run's compute consumers. A surviving orphan worker is not adopted; its run remains active until the worker exits and a later poll can reconcile it. B013 supplies worker supervision, B014.1 durable job state, B014.2 the current SDK worker flow, B014.4 simulated compute lifecycle metadata, B014.5 pre-dispatch selector/environment resolution, and B014.6 worker/resource integration. `brickhouse run` still explicitly fails; its direct-script lifecycle has not been composed. A dead server releases the kernel lock; stale PID data does not prevent recovery. POSIX local filesystems are the tested scope; Windows and network filesystems are not claimed. Metadata schemas 1–11 upgrade transactionally to schema 12 under workspace ownership; workspace format version 1 remains unchanged.

All processes must propagate cancellation and exit status. Terminate descendant process groups after a configurable grace period; avoid orphan kernels. Bound queue length, concurrent jobs, query results, logs, and staged files. Reject overloaded requests with a documented error rather than exhausting the host.

B013.1 adds the internal `run_python_worker()` launch primitive: resolved absolute interpreter/script paths, explicit cwd, size-limited immutable JSON context, a minimal environment, concurrent bounded stdout/stderr capture, and the real child exit code. B013.2 adds versioned private worker messages and attempt-scoped bearer authentication. B013.3 adds timeout/cancellation, POSIX process-group escalation, attempt-token revocation, safe staging cleanup callbacks, and SQLite worker outcome records. B014.1 adds immutable job definitions/submissions, task snapshots, validated DAG metadata, distinct attempt identities and accurate state persistence. B014.2 composes pinned-SDK workspace source import, single-task Python dispatch, status polling, and bounded persisted output. B014.3.1 adds sequential DAG dispatch with persisted dependency-failure skips; B014.3.2.1 implements bounded per-task retry attempts; B014.3.2.2 implements run concurrency admission; B014.3.3 reconciles active runs after restart. B014.4 adds simulated cluster identity/lifecycle, run-scoped consumer tracking and generation-based invalidation in metadata schema 7; B014.5 resolves selected execution context; B014.6 binds all seven selected job variants to worker consumers and cancels/reaps active workers on all-purpose compute invalidation. The local runtime does not yet provide worker-side Spark/Sparkless or table-service APIs.

## Persistence and recovery

SQLite migrations are versioned and transactional where supported. Refuse to open a newer workspace format with an older binary. Test upgrades from supported prior versions; define backup requirements before destructive migrations. SQLite WAL and filesystem locking assumptions must be documented; network filesystems are unsupported until tested.

Use an operation journal for transitions spanning metadata and Delta/files. B008.3 implements local Delta intent, a payload/options fingerprint, per-table monotonic transaction version, and final commit version in SQLite schema 4. Before replay, it requires the matching provider transaction version and exact operation/fingerprint entry in recent Delta history; a confirmed transaction without its exact history version is insufficient. Known committed replays return the original version, changed-payload operation-key reuse fails, and unconfirmed outcomes block further writes for that table until the same operation is reconciled. History lookup is bounded to 100 recent commits; expired or unavailable evidence stays uncertain. B008.4 deletes a managed table's files before its registration, so interrupted recursive cleanup can be retried from the still-present registration; external drop removes only metadata. The table's operation rows are pruned atomically with registration removal. This local recovery path does not yet cover jobs, external side effects, or separate-workspace/host writers. Avoid blindly rerunning a Python job whose external effects cannot be reconciled.

Back up a quiesced workspace or use a coordinated snapshot procedure that captures consistent SQLite, Delta logs/data, and provider state. Copying a live SQLite main file alone is not a backup. External tables need a manifest and an explicit inclusion policy; do not delete or duplicate them as an incidental backup action. Restore tests must read real data and job history.

## Observability

Structured events include workspace, request, job/run/task/attempt, statement, table, operation, and Delta version IDs as applicable. Preserve user stdout/stderr separately from service events. Redact known secrets and avoid logging SQL parameter values by default; redaction cannot guarantee arbitrary user code will never reveal secrets.

The server exposes local health, package version, capability reports, catalog/schema REST routes, classic cluster lifecycle routes, Python workspace-file import and the bounded Python job API. Provider detection uses package metadata only and does not import optional modules. B008.2 adds the explicit local `DeltaRsTableService` through the `brickhouse[delta]` extra; B008.3 adds its durable operation journal and replay reconciliation, and B008.4 adds external deregistration and safe local managed cleanup. The table service is not composed into Sparkless or SQL workers. SDK behavior is tested against the pinned client on loopback and does not establish Databricks workspace compatibility. Report simulated cluster metadata clearly. Metrics include queue time, execution time, failure category, result bytes, and worker resource use where supported. Do not silently send telemetry outside the machine.

## Build and CI

Use a standard Python build backend and a reproducible development lock. `databricks-sdk==0.153.0` is pinned in the developer lock for local catalog/schema protocol tests and is not a BrickHouse runtime dependency. The base BrickHouse install still has no runtime dependencies. The optional `delta` extra pins `deltalake==1.2.1` and `pyarrow==23.0.1`, matching the local provider integration evidence in B008.2; those exact versions are the tested profile. Keep native provider/client version fixtures separately identifiable.

Suggested CI lanes: lint/type checks; domain tests; native table tests; SDK/process integration; clean wheel installation; JVM-free/offline golden path; optional-extra workflows. All consume reference fixtures locally and receive no personal Databricks credentials. The local suite exercises package/CLI bootstrap, workspace configuration/ownership/lifecycle, local catalog/schema and classic cluster API calls using the pinned SDK, Python source upload and single-script job execution/output, schema migration, worker failure/timeout/cancellation, bounded output, and a real local Delta provider service for staged create/read/append/overwrite, journal replay recovery, and ownership-safe removal. Sparkless execution, SQL integration, DAG/retry/restart behavior, and Databricks workspace behavior remain unverified.

The optional manual `workflow_dispatch` capture workflow at `.github/workflows/databricks-reference.yml` uses the owner's personal Databricks account to resolve selected behavior questions and refresh sanitized fixtures, following [document 15](15-personal-databricks-verification.md). It is restricted to `main`, a curated probe, a bounded serialized run, job-scoped credentials, and a sanitized one-day artifact. The owner reports `DATABRICKS_TOKEN` is configured as an Actions secret; the non-secret `DATABRICKS_HOST` repository variable must be configured separately. A bounded local capture verified the Free Edition workspace, used one existing serverless 2X-Small SQL warehouse for one synthetic statement, and returned it to its initial stopped state. The host and token are not stored in tracked configuration. There are no automatic push/PR/schedule triggers or required CI dependency. Normal tests and runtime must not load `.env` or inherit real-workspace authentication. The GitHub workflow has not been dispatched; secret/variable availability and artifact upload remain unverified.

Initial platform candidates are Linux x86_64 and macOS arm64 on Python 3.11/3.12. They become supported only after wheel and workflow gates pass. Test Windows and additional architectures before advertising them. Do not force users to install a Rust compiler to compensate for an untested wheel matrix.

The selected local fixture limits and overload/expiry/cancellation assertions are specified in [document 16](16-phase-0.1-initial-release.md#local-fixture-limits-and-overload-behavior). They are future acceptance settings, not new fields currently accepted by version-1 config or Databricks defaults. B045 verified the pinned kernel's first session request over local TLS/auth; [its report](../../artifacts/conformance/B045-sql-connector-loopback.md) records the port and custom-CA constraints. B021 still must prove session handling and real query results.

## Distribution and release

Reserve/configure repository and package ownership separately. A package-name lookup does not reserve a PyPI name. Resolve any name collision before publishing, preserving the agreed project identity where possible. The plan does not create a repository, reserve names, or choose final legal ownership/license terms.

A release candidate includes wheels/sdist, install report, capability snapshot, dependency/native version inventory, notices, changelog, migrations, and example workflows. Public examples must execute against that candidate. Publish only with owner authorization; do not embed publishing credentials in project files.

## Supply chain boundary

Pin copied source provenance and audit intentional private-API use. Validate optional native/service artifacts independently. Separate local development dependency overrides from public install requirements. Environment creation for jobs must use an explicit dependency manifest and provisioning policy; arbitrary job-time package installation is unsupported initially.
