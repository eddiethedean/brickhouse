# 06 — Jobs, notebooks, and dbutils

## Runtime strategy

Replace Spark-oriented job launching with a BrickHouse supervisor and fresh Python worker. Reuse selected Minilake task validation/lifecycle ideas only after adapting them to persistent instance-scoped state. The worker gets a run ID, attempt ID, profile, parameters, namespace, environment reference, workspace mapping, cancellation channel, and run-scoped internal credential.

Use the resolved environment's interpreter, not an unqualified `python3` from PATH. Initially require the current supported BrickHouse environment. Later environment specifications can create cached virtual environments from locked dependencies. Do not automatically run arbitrary library installation requests from a cluster configuration.

**B013 implementation:** `brickhouse.runtime.run_python_worker()` resolves the selected interpreter and script to absolute paths, preserves a virtual environment interpreter symlink, sets an explicit working directory, disables shell execution, and snapshots JSON-only attempt context into `BRICKHOUSE_RUN_CONTEXT_JSON`. The context is capped at 16 KiB. Each child starts without inherited credentials, Python import paths, or session state. Stdout and stderr are drained concurrently with 1 MiB defaults and a 64 MiB per-stream maximum. Results contain the actual exit code, bounded text, truncation flags, limits, and resolved paths. The version-1 private message envelope is capped at 64 KiB and rejects malformed JSON, unknown fields and invalid scopes. A random per-attempt bearer is delivered only in `BRICKHOUSE_WORKER_TOKEN`; its digest is kept by the parent. Credentials are revoked after termination, and captured output redacts the token. Timeouts and cancellation signal the POSIX process group, escalate after a bounded grace period, reap the direct child, and invoke caller-supplied safe staging cleanup. B064.4 keeps the same deadline while output-pipe readers drain, so a descendant holding inherited pipes after the leader exits cannot bypass timeout or cancellation supervision. Metadata schema 5 stores the real exit result and cleanup status without logs or credentials. See [ADR 0019](../decisions/0019-worker-private-authentication.md) and [ADR 0020](../decisions/0020-worker-supervision-and-outcomes.md).

**B014.1 implementation:** `WorkspaceContext.jobs` exposes an internal SQLite repository for immutable, bounded Python-script job definitions, immutable submission snapshots, workspace-wide idempotency tokens, task DAG snapshots, durable attempts, and explicit state transitions. Metadata schema 6 adds the job/run/task/attempt tables with foreign keys, content fingerprints, legal-transition and terminal-result checks, and immutable terminal history. Invalid dependencies, cycles, unsupported task kinds, credential-shaped setting keys, and changed token replays fail explicitly. Interrupted runs retain unknown exit status and do not convert pending tasks into successful work. This is a persistence contract only: it does not dispatch workers, expose SDK/HTTP routes, recover active runs automatically, return durable logs, or implement concurrency/retry policy. See [ADR 0022](../decisions/0022-durable-job-state.md) and [B014.1 evidence](../../artifacts/conformance/B014.1-durable-job-state.md).

**B014.4 implementation:** `WorkspaceContext.compute` persists simulated classic all-purpose cluster identities and run-scoped new/shared job compute in metadata schema 7. The pinned `databricks-sdk==0.153.0` loopback profile implements classic cluster create/get/list/edit/start/restart/terminate/permanent-delete. Standard/dedicated access labels and the `spark35-local-v1` alias are explicit local mappings; unmapped Databricks Runtime strings, access modes, Photon, JVM-specific settings, policies, and cloud-specific effects fail explicitly. A controlled clock drives idle termination. Consumers register before dispatch, shared compute starts for the first consumer and stops after every planned consumer releases, while all-purpose identity survives termination and can autostart when requested. Generation numbers and append-only events record session invalidation. These records do not allocate compute, enforce access isolation, or execute workers. See [ADR 0023](../decisions/0023-local-classic-compute-lifecycle.md) and [B014.4 evidence](../../artifacts/conformance/B014.4-classic-compute-lifecycle.md).

**B014.5 implementation:** `ExecutionContextResolver` maps the pinned task wire shapes to immutable internal context before dispatch. It accepts Python script/notebook tasks with normalized `/Workspace/...` paths, declared serverless environment version `1` and installed dependency pins, or classic inline/shared/existing compute. It records run/task identity, profile, resource ID/key/generation, task arguments, timeout, retries and effective settings. Serverless tasks require `disable_auto_optimization=true` and receive ANSI/UTC defaults. Unmapped clients/versions/dependencies, installs, compute objects, conflicting selectors, unsupported conditions/task types, SQL warehouse notebooks, credential-shaped parameters and invalid paths fail explicitly. An omitted or zero timeout means no timeout; positive values use the local worker's 24-hour maximum. This slice does not check file existence, upload files, dispatch a child, schedule retries, or claim workload compatibility. See [ADR 0024](../decisions/0024-pre-dispatch-execution-context.md) and [B014.5 evidence](../../artifacts/conformance/B014.5-execution-context-resolution.md).

**B014.2 implementation:** the pinned `databricks-sdk==0.153.0` loopback routes accept SDK multipart workspace imports (`SOURCE`/`PYTHON`) under normalized `/Workspace/.../*.py` paths and persist source bytes atomically under the owned workspace `files/` directory. Imports are capped at 1 MiB. Job tasks use resolved local serverless/classic selectors and mapped environments; `/run-now` submits saved parameters or bounded single-task `python_params`. Idempotency tokens replay the same run while it is active or terminal. `/runs/get` maps observed local state to SDK lifecycle/result enums; `/runs/get-output` returns at most 1 MiB stdout and 1 MiB stderr (`logs`/`error`) with truncation metadata for a single-task run. Metadata schema 8 stores immutable attempt output and validates upgrades from schema 7. B014.3.2.1 adds retry policy, and B014.3.2.2 adds bounded concurrency admission; output for multi-task runs and output while running remain unsupported. Each fresh child process runs with a minimal environment and immutable run context; B014.6 now binds classic worker starts/stops to simulated resource lifetimes. B015.1.1–B015.1.3 add an opt-in worker Sparkless session and authenticated registered-table reads; B018.1.1 adds a bounded append for existing registered Delta tables. B022.3.1 adds 24-hour worker-output retention: a controlled-clock sweep clears persisted stdout/stderr while preserving attempt/run history, and `/runs/get-output` includes `logs_expired`. B022.4 verifies that a serverless-local worker timeout after a real Delta append leaves one timed-out attempt and the committed version intact after workspace reopen; a separate pre-commit failure retries into a distinct attempt and one commit. Timeouts are not retried unless explicitly enabled. These are local worker lifecycle checks, not Databricks service semantics. Expiry is lazy on output retrieval or explicit repository maintenance; no background scheduler is present. No cloud compute or Databricks runtime parity is claimed. See [B022.4 evidence](../../artifacts/conformance/B022.4-serverless-timeout-commit.md), [ADR 0025](../decisions/0025-sdk-python-job-flow.md), and [B014.2 evidence](../../artifacts/conformance/B014.2-workspace-files-sdk-jobs.md).

**B014.3.1 implementation:** the service accepts up to ten validated Python script tasks and dispatches them sequentially in a stable topological order. The repository independently refuses to queue an attempt until every dependency succeeded. Failed, cancelled, skipped, or interrupted dependencies produce a persisted `SKIPPED` task with zero attempts; independent tasks continue, and the run is failed after all eligible work has a truthful terminal outcome. Only default `ALL_SUCCESS` scheduling is supported. B014.3.2.1 adds bounded task retries; B014.3.2.2 admits concurrent runs within a local process limit. B014.3.3 reconciles active runs after service restart. Multi-task SDK output retrieval remains unsupported. B015.1.1–B015.1.3 add the selected worker Sparkless/read surface; B018.1.1 adds the bounded shared Delta append. See [ADR 0026](../decisions/0026-sequential-job-dag-dispatch.md) and [B014.3.1 evidence](../../artifacts/conformance/B014.3.1-dag-dispatch.md).

**B014.3.2.1 implementation:** validated task retry settings are now executed as a bounded local policy. Nonzero worker exits retry up to ten times, timeout retries require `retry_on_timeout=true`, and `min_retry_interval_millis` is honored with an interruptible wait. Each attempt has a distinct durable identity and immutable output. Launch failures, cancellation, and interrupted attempts do not retry. The API reports initial/retry attempts using the SDK's zero-based attempt number while persisted attempt numbers remain one-based. `max_concurrent_runs` admission is still B014.3.2.2. See [ADR 0027](../decisions/0027-bounded-task-retries.md) and [B014.3.2.1 evidence](../../artifacts/conformance/B014.3.2.1-retry-attempts.md).

**B014.3.2.2 historical implementation:** each job accepted `max_concurrent_runs` from 1 through 4, and the process admitted at most four worker runs. B064 supersedes that admission policy: per-job limits now accept 1–10; at most two attempts dispatch at once and up to eight further runs persist in FIFO queue. Overflow returns HTTP 409 (`RESOURCE_CONFLICT`) before run creation. The scheduler preserves queue order, resumes undispatched entries after restart, and interrupts runs whose attempts had started. Reset revisions share one public Terraform job admission identity. See the [B064 review-fix evidence](../../artifacts/conformance/B064-phase-0.1-review-fixes.md); [ADR 0028](../decisions/0028-bounded-run-admission.md) records the earlier four-run policy.

**B014.3.3 implementation:** metadata schema 9 stores each worker PID and accepts an explicit interrupted outcome with no exit code. On service start and when a run is polled, the local job service checks persisted active attempts. If the worker PID is gone, it preserves already completed attempts and output, marks unknown in-flight worker and job attempts interrupted, and reports `WORKSPACE_RESTARTED`; it does not replay user code. If an orphan worker is still alive, the service leaves the run active and reconciles it after a later poll observes that process has exited. SDK output retrieval falls back to the latest attempt with persisted output if the current attempt was interrupted before capture. No cross-process worker adoption or replay guarantee is claimed. See [ADR 0029](../decisions/0029-active-job-restart-reconciliation.md) and [B014.3.3 evidence](../../artifacts/conformance/B014.3.3-active-run-recovery.md).

**B014.6 implementation:** each submitted classic job reserves planned consumers for its run. Immediately before a task, new/shared resources start for that consumer; an existing all-purpose cluster retains its ID and autostarts when explicitly resolved as terminated. Each worker receives the actual simulated resource ID, generation and state alongside its immutable per-attempt context. Task results release consumers; failed dependencies and service recovery also release reserved consumers, and the last released new/shared consumer terminates the resource. A monitor checks the selected all-purpose generation/state while user code runs. Restart or termination increments/changes the resource state, signals worker cancellation, and the worker supervisor terminates and reaps the POSIX process group. The pinned-SDK loopback corpus exercises all seven document 16 job variants, restart and termination during real work, service recovery without inferring success, and preservation of an already committed Delta table. Compute allocation remains simulated. B014.6 by itself ran plain Python without Spark/Sparkless sessions or job-facing table access; B015.1.2 now adds an opt-in Sparkless session when a worker imports `pyspark.sql`, while registered table access remains B015.1.3. See [ADR 0030](../decisions/0030-job-worker-compute-lifetimes.md) and [B014.6 evidence](../../artifacts/conformance/B014.6-job-worker-compute-lifetimes.md).

**B016.1 implementation:** every SDK Python task is launched through a small worker entry module that injects a fresh `dbutils` object into that script's global namespace. `dbutils.fs` maps `dbfs:/...` and `/dbfs/...` to `workspace/files/dbfs`, with symlink and parent-traversal rejection. `ls`, `head`, `put`, `cp`, `mv`, `rm`, and `mkdirs` perform real local operations; previews, writes, and recursive tree operations have explicit size/entry limits. `dbutils.widgets` supports text/dropdown/combobox/multiselect declarations, get/getAll and removal. Widget values start from defaults, then `name=value` task parameters, then matching run-now `python_params`; ordinary argv entries remain unchanged for the script. The state is constructed in each fresh worker, so declarations and values do not cross runs. Other filesystems, mounts, volumes, notebook utilities, and arbitrary dbutils methods are not provided. Direct Python filesystem access remains trusted code and is not sandboxed. See [ADR 0031](../decisions/0031-worker-dbutils-files-and-widgets.md) and [B016.1 evidence](../../artifacts/conformance/B016.1-worker-dbutils-files-widgets.md).

**B016.2 implementation:** `WorkspaceContext.secret_provider` holds explicit scope values and per-job scope grants in process memory only. An embedding caller configures values with `put(scope, key, value)` and authorizes a job with `grant_job(job_id, scope)`; these APIs do not persist values or grants, read `.env`, or accept public HTTP credentials. At each task attempt, the service snapshots only that job's granted scopes and sends the bounded payload to the child over a one-way stdin pipe. Values are absent from immutable worker context, run/job metadata, environment variables, command-line arguments and ordinary configuration. The worker exposes `dbutils.secrets.get/getBytes/list/listScopes`; ungranted scopes raise `PermissionError`, missing keys in granted scopes raise `KeyError`, and list methods expose only authorized scope/key metadata. Exact secret bytes are redacted from retained stdout/stderr before results are returned or journaled. Transformed/encoded values cannot be generally recognized. Values/grants are process-local and must be configured again after service restart. See [ADR 0032](../decisions/0032-process-memory-scoped-secrets.md) and [B016.2 evidence](../../artifacts/conformance/B016.2-process-memory-scoped-secrets.md).

**B016.3 implementation:** Python script workers expose `dbutils.jobs.taskValues.set/get` through a versioned, attempt-authenticated local socket to the parent repository; SQLite never opens in the child. Values must be strict finite JSON, each compact UTF-8 JSON representation is at most 48 KiB, and each run may define at most 250 distinct `(task, key)` pairs. A task can update its key within an attempt. Rows are keyed by run, task, attempt, and key; a reader can access only transitive declared upstream tasks after they succeed, and the latest successful attempt supplies the value. Failed-attempt rows remain attributable to that attempt but are not visible downstream. `get` raises `ValueError` for an unknown task or missing value unless a non-`None` `default` is supplied; `debugValue` is accepted but only applies outside a job, so it never masks a missing value in a job worker. `set` returns `True`. Unsupported `dbutils.jobs` methods raise `DbutilsOperationNotSupportedError`. This script-task adapter follows the documented task-value contract, while Databricks documents `dbutils.jobs.taskValues` for Python notebooks; notebook execution/output is still B017. Existing attempt stdout/stderr remains the captured job output after the worker exits; no notebook exit or live output API is claimed. See [ADR 0033](../decisions/0033-attempt-scoped-task-values.md) and [B016.3 evidence](../../artifacts/conformance/B016.3-attempt-scoped-task-values.md). Databricks contract references: [dbutils taskValues reference](https://docs.databricks.com/aws/en/dev-tools/databricks-utils) and [task values guide](https://docs.databricks.com/aws/en/jobs/task-values).

## Job lifecycle

Persist job definitions, immutable submitted settings, run/task IDs, attempt numbers, timestamps, parameters, state transitions, bounded logs/output, and error details. Validate task types and dependencies before execution. Map internal states to the pinned Databricks client's enums at the API boundary. B014.1 supplies the durable definition/submission/task/attempt metadata; B014.2 composes upload and the initial single-script SDK flow; B014.3.1 schedules bounded sequential DAGs and propagates failures; B014.3.2 implements bounded retries and local run admission. B014.3.3 still owns restart reconciliation, and B014.6 owns worker/resource lifetime behavior.

Required behavior: idempotent submission where the API provides a token, dependency validation, bounded concurrency, timeout, cancellation of the process group, process reaping, retries, and restart reconciliation. B013 provides the internal cancellation/reaping and per-attempt outcome primitives; B014 must compose them into job/run state. A terminal state is immutable except for an explicitly modeled repair/new attempt. Skipping a task because its dependency condition failed is valid; skipping an unsupported requested task as if execution succeeded is not.

Cancellation is an observable lifecycle: request stop, signal worker, escalate after grace, reap, persist terminal state. A write that already committed remains committed; cancellation must not fabricate rollback. Retry policy consults mutation idempotency records.

## Python compatibility

Explicit Sparkless imports are the first supported mode. **B015.1.1 implementation:** the managed worker installs a lazy import finder in its child process. It maps `pyspark.sql`, `pyspark.sql.functions`, `pyspark.sql.types`, and `pyspark.sql.window` to the corresponding public Sparkless 4.15.2 exports while preserving object identity for DataFrame/function/type/window objects inside the worker. The `SparkSession` name is a BrickHouse facade backed by the public Sparkless constructor. No top-level `pyspark` package is shipped and the parent interpreter is unchanged. The worker rejects preloaded or import-path PySpark packages and unsupported namespaces (`pyspark.rdd`, `pyspark.ml`, and `pyspark.java_gateway`) with explicit BrickHouse import errors. Import availability does not claim operation-level Spark parity.

**B015.1.2 implementation:** when user code imports `pyspark.sql`, the worker validates its immutable profile and creates one Sparkless session before that import returns. Serverless applies ANSI/UTC defaults; classic standard/dedicated are limited to `spark35-local-v1` with explicit ANSI/timezone settings and matching access mode. The selected builder supports validated `.config(key, value)` and `.getOrCreate()`. DataFrame construction/range and selected read-only SQL run through an owner-thread facade; B018.1.1 adds only the registered Delta append described below. RDD, JVM, reader, and catalog access remain blocked. Plain Python workers do not load Sparkless; invalid Spark-profile context fails when a script requests `pyspark.sql`. `appName`, `master`, and `option` are unsupported.

**B015.1.3 implementation:** jobs with the attempt-authenticated parent service attach a read-only Sparkless external-catalog provider inside the worker. `SparkSession.table()` and read-only SQL resolve only registered names through the parent catalog and `DeltaRsTableService`; the returned public descriptor contains the stable table ID, canonical location, schema, provider, and exact Delta version. Missing names and an unregistered Delta path fail; workers without the authenticated service cannot read catalog tables. SQL mutations remain explicit errors. B018.1.1 adds a narrowly scoped DataFrame writer callback: only `format("delta").mode("append").saveAsTable()` to an existing registered table is allowed. The worker sends Arrow IPC to the authenticated parent service; the parent verifies the table ID, canonical location, and expected version before committing through `DeltaRsTableService`. Other writer modes, paths, options, partitions, and table creation fail explicitly. The 64 KiB worker message limit bounds descriptors and write requests. See [B015.1.3 conformance](../../artifacts/conformance/B015.1.3-worker-registered-tables.md). B015.2 owns the separate `delta.tables.DeltaTable` facade.

**B015.2 implementation:** managed workers expose `delta.tables.DeltaTable` through an isolated import facade. `forName`, `forPath`, and `isDeltaTable` use the attempt-authenticated parent service and accept only registered Delta identities/canonical paths. `forName` rejects temporary views; `forPath` rejects unregistered Delta directories; `isDeltaTable` reports registration. `toDF` and `alias` read via the existing Sparkless session/provider. `delete`, `update`, `merge`, restore, and vacuum operations fail with `UnsupportedWorkerDeltaOperationError`; DeltaTable does not bypass BrickHouse's common mutation service. Conflicting `delta-spark` packages and unsupported namespaces are rejected without changing the parent interpreter. The pinned-SDK loopback job read actual committed rows and preserved version 0; see [B015.2 conformance](../../artifacts/conformance/B015.2-worker-delta-table.md). No new Sparkless API is required for this subset.

Do not ship a top-level `pyspark` wheel that overwrites the genuine package. Do not rewrite user source with regex. Unsupported `pyspark.ml`, `rdd`, Java gateways, arbitrary jars, Scala tasks, and JVM-specific configuration must produce clear capability errors until a native equivalent is deliberately implemented.

The `delta.tables.DeltaTable` facade remains distinct from installing `deltalake`. Its current read-only subset is implemented; do not add mutation methods or builders until the table-service contract can preserve registered table identity, exact commit versions, and bounded work. Never create an independent unmanaged writer path for registered tables.

**B018.1.1 implementation:** a parameterized pinned-SDK script resolves one job-granted secret, constructs explicitly typed rows, and appends them through Sparkless to an existing registered Delta table. The attempt-authenticated service transports at most 32 KiB of Arrow IPC and 100,000 rows; the parent checks table identity/location/current version, then uses the journaled Delta service with `expected_version`. A declared dependent task reads both the task value and committed rows. The test checks persisted per-task output and compares the same rows/schema through a fresh Sparkless session and SDK SQL statement execution. This report captures the first classic-standard local shape; [B018.1.3](../../artifacts/conformance/B018.1.3-g2-compute-profiles.md) now covers all seven job selectors and [B018.1.4](../../artifacts/conformance/B018.1.4-g2-warehouse-profiles.md) covers the three local warehouse profiles. See [B018.1.1 evidence](../../artifacts/conformance/B018.1.1-job-to-delta-data-flow.md).

**B018.1.2 implementation:** focused pinned-SDK jobs verify truthful upstream failure propagation, distinct retry attempts and output, and cancellation during classic compute restart/termination with worker-descendant reaping. They also confirm parameters/widgets, scoped secrets, and task values stay isolated between runs and failed attempts; a Delta commit made before interruption remains readable. These are local worker semantics, not remote Databricks behavior, and cancellation here is triggered through compute interruption rather than a public job-cancel route. See [B018.1.2 evidence](../../artifacts/conformance/B018.1.2-job-lifecycle-isolation.md).

**B018.1.3 implementation:** the same two-task orders workflow now runs through all seven selected serverless/classic-standard/classic-dedicated job selectors using the pinned SDK loopback adapter. Each producer reads parameter widgets and a granted secret, appends typed data to the shared registered Delta table, and publishes a task value; each dependent reader observes that commit. Captured task output and final data/schema are checked across all profiles. Serverless creates no classic resource; new compute is per task and terminates after release; shared resources terminate after both task consumers release; existing all-purpose IDs remain running. Classic compute lifecycle records are simulated. See [B018.1.3 evidence](../../artifacts/conformance/B018.1.3-g2-compute-profiles.md). Warehouse readers for these G2 commits remain B018.1.4.

**B018.1.4 implementation:** a pinned-SDK job appends an order to the registered Delta table; the test selects exact Delta version 1 and compares its schema/data with a fresh Sparkless read. It then reads the same table through local serverless (`PRO` plus the serverless flag), pro (`PRO`), and classic (`CLASSIC`) warehouse profiles. Statement result schemas and values match the job-produced commit, leases release, and the Delta version remains unchanged. Warehouse allocation remains simulated, and the test does not establish remote SQL compatibility. See [B018.1.4 evidence](../../artifacts/conformance/B018.1.4-g2-warehouse-profiles.md).

**B018.2 installation evidence:** the base wheel installs pinned Sparkless, delta-rs, PyArrow, and SQLGlot, with all four notebook distributions absent. ## dbutils implementation plan

| Surface | Proposed behavior |
|---|---|
| `fs.ls/head/put/cp/mv/rm/mkdirs` | Implemented for real local `dbfs:/` and `/dbfs/` paths under `workspace/files/dbfs`; traversal and symlinks rejected, operations bounded |
| `widgets.text/dropdown/combobox/multiselect/get/getAll/remove/removeAll` | Implemented in the SDK Python worker with defaults, `name=value` task parameters, then run-now override precedence; state is attempt-local |
| `secrets.get/getBytes/list/listScopes` | Implemented for embedding-configured process-memory values and explicit job scope grants; values cross to workers over a one-way pipe and retained raw values are redacted |
| `jobs.taskValues.set/get` | Implemented for SDK Python job scripts over the private parent service; finite JSON, 48 KiB/value, 250 distinct task/key pairs per run, attempt isolation, successful transitive upstream reads, non-`None` default, and explicit unsupported methods; not notebook parity |
| `notebook.run` | Child run using parameter scope, timeout, output contract, and parent cancellation |
| `notebook.exit` | Controlled worker signal converted to notebook output, not accidental process failure |
| Context getters | Versioned documented subset of run/job/path context |
| Mounts and credential utilities | Explicit unsupported state until meaningful native semantics exist |

The SDK's native secrets getter calls an endpoint rejected by the reviewed Minilake server. Installing the SDK does not close that gap. Inject a scoped provider into the managed runtime; never place the entire secret store in environment variables or public responses. Capture/redact secret-bearing logs and document limitations of redaction for transformed values.

## Notebook execution

**B017.1 implementation:** `brickhouse.notebooks.execute_ipynb()` is an optional
Python `.ipynb` execution primitive using pinned `ipykernel==7.4.0`,
`jupyter-client==8.10.0`, `nbclient==0.11.0`, and `nbformat==5.11.1` from
`brickhouse[notebooks]`. Each call provisions an isolated kernel specification
for an explicit interpreter, uses private temporary Jupyter/IPython directories,
and starts with the minimal worker environment and bounded JSON context. The
kernel bootstraps its profile-bound Sparkless session and local `dbutils` inside
the child namespace. One optional code cell tagged `parameters` supplies defaults;
finite JSON overrides are injected immediately after it. The runner saves output
cells atomically on success or cell failure and raises `NotebookExecutionError`
after persisting the failure artifact. The source notebook is never overwritten.
The original B017.1 real-kernel report uses Sparkless 4.15.0 and verifies Spark/DataFrame work,
widget/DBFS operations, output capture, per-call kernel isolation, credential
non-inheritance, and failure artifacts; see [B017.1 evidence](../../artifacts/conformance/B017.1-ipynb-kernel.md).
The current 4.15.2 pin and notebook-extra matrix are recorded in the [release candidate bundle](../../artifacts/releases/0.1.0/README.md).
The supported profile is a local execution subset, not Databricks notebook parity.

**B017.2 implementation:** `brickhouse.notebooks.execute_databricks_python_source()` accepts a marked `.py` export whose first line is `# Databricks notebook source` and parses `# COMMAND ----------` cell boundaries and `# MAGIC` markers structurally. It converts Python cells, runs `%sql` through the injected Sparkless session and publishes `_sqldf`, retains `%md` as Markdown, and handles `%run` inline in the caller's Python namespace. `%run` targets must be relative, marked `.py` source-export notebooks inside the same source tree; missing, escaping and cyclic references are rejected before a kernel starts. The original source remains unchanged. This follows Databricks' [source import/export format](https://docs.databricks.com/aws/en/notebooks/notebook-export-import?language=SQL) and the documented [magic and `%run` behavior](https://docs.databricks.com/aws/en/notebooks/notebooks-code) ([inline scope contract](https://docs.databricks.com/aws/en/notebooks/notebook-workflows)). The focused local suite verifies all four handlers and shared scope using a real kernel; see [B017.2 evidence](../../artifacts/conformance/B017.2-source-format-magics.md).

The source-export subset rejects `%r`, `%scala`, `%sh`, `%fs`, `%pip`, `%uv`, unknown magics, unsupported magic options, and non-Python source files before launching a kernel. It does not map absolute workspace paths, treat plain Python modules as `%run` notebooks, resolve serverless base-environment manifests, or claim SQL semantics beyond the local Sparkless session. SQL result rendering currently collects the local result into the notebook output.

**B017.3 implementation:** `dbutils.notebook.run()` accepts relative local `.ipynb` or marked Python `.py` child notebooks inside the selected source root. Each child receives its own fresh kernel and session, a copy of worker context, and the run argument map as string widget values. Child variables and cell outputs remain private; the caller receives the child's string from `dbutils.notebook.exit()`, or an empty string if it completes without one. `exit()` stops later cells. Arguments must be ASCII strings and total at most 16 KiB; exit values are UTF-8 and at most 1 MiB; `timeout_seconds=0` disables the total deadline and positive values are monotonic deadlines up to 24 hours. Failures and timeouts propagate as explicit errors. Tests verify child timeout cleanup and parent-cell cancellation of both the child kernel and its spawned subprocess; see [B017.3 evidence](../../artifacts/conformance/B017.3-child-notebook-outcomes.md). Absolute workspace paths, remote children, full SDK job/task/run-now parameter merging, and child artifact retrieval are not implemented.

**B017.4 implementation:** notebook execution accepts both the nested local context envelope and the flattened worker context produced by the scheduler. It validates the profile and selected interpreter before creating a kernel. Serverless requires environment version `1` and a `serverless-python<major><minor>-local-v1` mapping that matches the selected interpreter; the exact pinned `ipykernel`/Sparkless packages and each requested dependency must already be installed. Classic standard/dedicated require the mapped `spark35-local-v1` runtime alias, matching access mode and explicit ANSI/timezone values; they reject serverless environment metadata. No package installation or environment creation occurs. Tests run all three profiles with actual kernels, retain Python and Sparkless session state between cells, and prove a later invocation starts with fresh globals/config. Invocation parameters override tagged-cell defaults, while resolved `dbutils.widgets` values override notebook widget defaults. B017.4 also retains the simulated classic compute identity/generation needed for supervision. See [B017.4 evidence](../../artifacts/conformance/B017.4-notebook-context.md).

**B017.5 implementation:** the pinned Jobs SDK loopback adapter dispatches selected single-task `NotebookTask` definitions to real local kernels for serverless and classic standard/dedicated new, existing, and shared selections. Job base parameters reach the notebook and run-now values override them. Notebook PEP 723 environment metadata is used when the job omits an environment; a job-level environment wins when supplied. Marked Python source exports execute in all three profile families with metadata retained during conversion. A compute-generation watcher interrupts the associated kernel worker after restart/reset or termination; worker timeout follows the same bounded cleanup path. Tests prove supervisor/kernel/descendant exit, fresh replacement state and preservation of committed Delta data. Parent-cell cancellation of nested child notebooks is covered by B017.3. The local resource lifecycle is simulated, and these SDK/model tests do not establish Databricks service behavior or full parameter-merge parity. Only one-task notebook output is exposed; multi-task `runs/get-output`, remote notebooks, dependency installation, and broader runtime semantics remain unsupported. See [B017.5 evidence](../../artifacts/conformance/B017.5-notebook-compute-interruption.md).

Inject `spark`, `dbutils`, and supported `display` helpers into a fresh kernel. Capture cell outputs, execution counts, errors, and notebook result artifacts. Parameterization may use Papermill, but widgets and job parameter precedence remain BrickHouse contracts. Timeout and cancellation must reach the kernel and descendants.

`%pip` and interpreter restart require environment lifecycle design; initially reject them with a clear explanation. Do not permit a notebook dependency installer to introduce Spark/JVM runtime silently.

## Minimum end-to-end job test

Use the real SDK to upload a Python script, create a job, submit it, poll it, and retrieve output. The script reads parameters and one scoped secret, builds/transforms a DataFrame, writes a managed Delta table, and returns a count. A second task reads that table by name. Validate output and data through the SQL API, then restart the server and repeat the read.

Negative cases: invalid namespace, unsupported task type, missing workspace file, bad parameter type, failing dependency, worker crash, timeout, cancellation during a write, secret access outside job scope, repeated submission token, and restart with an active run. No Java process or external compute request may occur.

Repeat the bounded workflow for serverless and classic new/existing/shared compute, with explicit environment/runtime mappings and all three local SQL warehouse types. Add pre-dispatch selector/config errors, real compute/session termination, and notebook profile variants. [Document 17's test designs](17-serverless-and-classic-compute.md#local-test-designs-and-reference-questions) define the mode-specific assertions and later cases.

## Preparation for later self-hosting

Local execution stays the emulator contract through phases 0.1–0.9. Keep PIDs, POSIX signaling, private sockets/pipes, interpreter paths and filesystem staging contained in runtime adapters; preserve durable job/attempt identity independently. B048 reviews actual boundaries using existing workload evidence. Local authorization and fresh processes do not claim authenticated network execution or sandboxing.

[Document 18](18-self-hosted-platform.md) places deployed identities/secrets in SH.1, real script/kernel/serving isolation in SH.3 and remote placement in SH.4, all after B049's stability gate. Remote attempts require enrolled/revocable workers, explicit environment/artifact identity, coordinator leases/generations validated at commits and state transitions, and truthful handling of partitions, stale completion and cancellation races. Reassignment reconciles Delta effects before replay and never promises exactly-once arbitrary Python effects. This is job distribution; a distributed Sparkless query is a separate future research decision.
