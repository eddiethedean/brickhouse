# 05 — Catalog, storage, and SQL contracts

## Implemented metadata slice

B007.1 adds SQLite metadata schema version 2 without changing workspace format version 1. It assigns immutable UUIDs to catalog and schema rows and provides instance-scoped catalog/schema readers plus managed/external table-registration repositories. Table locations are local canonical paths, managed paths reserve `tables/<table-id>` under the workspace, and location uniqueness catches symlink aliases. Metadata schema 1 is upgraded under the workspace owner lock. These repositories reserve identities and ownership only; they do not create directories or Delta tables or read/write data. See [ADR 0009](../decisions/0009-catalog-identity-and-location-registration.md) and [B007.1 evidence](../../artifacts/conformance/B007.1-catalog-identities.md).

B007.2 adds `parse_identifier()` and a `NamespaceState` created per caller session. The initial name profile resolves one-part tables in current catalog/schema, two-part tables in current catalog plus explicit schema, and three-part tables by explicit catalog/schema. Backticks can delimit parts containing dots; doubled backticks escape a literal backtick. Lookup is case-insensitive, missing and ambiguous matches are explicit errors, and `use_catalog` resets schema to `default`. The internal Sparkless session adapter uses this state for registered table lookup; this parser is not SQL parsing, SQL Path, or temporary-view resolution. See [ADR 0010](../decisions/0010-identifier-resolution-and-session-namespaces.md), [local evidence](../../artifacts/conformance/B007.2-identifier-resolution.md), and the separate [sanitized reference capture](../../artifacts/conformance/B007.2-identifiers-reference.md).

### Implemented SQL statement core (B011.1)

B011.1 adds a SQLGlot 30.24.0 Databricks-dialect parser and AST planner. One statement is parsed, classified, and bound against a caller-scoped namespace before execution. The current local core routes SELECT projection, predicates, `COUNT`/`SUM` with grouping, and one inner equijoin through the current pinned Sparkless 4.15.0 session; the original B011.1 report retains its exact 4.14.1 environment provenance. Selected schema and managed Delta table create/drop statements use `CatalogService` and the journaled `DeltaRsTableService`; CTAS reads from Sparkless before registering and committing its target. Query aliases are normalized in the AST to match the selected Sparkless SQL behavior. The exact local fixture, Delta commits, errors, and limits are recorded in [B011.1 conformance](../../artifacts/conformance/B011.1-sql-initial-corpus.md).

The B011.1 SQL core does not include table mutations, catalog create/drop syntax, CTEs, nested queries, path/table functions, outer joins, or self-joins. Unsupported syntax is rejected during planning; engine exceptions propagate without retrying another executor. SQLGlot does not establish Spark or Databricks semantic parity. B011.2–B011.6 and B019/B021 continue the release corpus. B019.1 is split into seven SQL fixture slices for scalar/null behavior, aggregates/decimals, dates/timezones, nested collections, joins, DDL/errors, and serverless/classic session profiles.

### Implemented statement API slice (B011.2)

Metadata schema 17 stores statement request text, typed parameter values, warehouse identity, request namespace, lifecycle state, terminal error, result limits and counts; result manifests and chunks use separate bounded tables. Metadata schema 18 extends the Delta operation journal for selected SQL UPDATE/DELETE operations and terminal no-op/provider-failure outcomes; schema 19 adds the selected SQL MERGE operation mode while preserving prior journal rows. The pinned `databricks-sdk==0.153.0` loopback client can submit and poll `/api/2.0/sql/statements`, retrieve indexed chunks, and recover successful results after a service restart. Omitted `wait_timeout` executes before returning; `wait_timeout="0s"` returns `PENDING`, and the first poll claims and executes the request. A `RUNNING` statement interrupted by service restart is marked `FAILED` without replay. Named primitive parameters are validated and persisted separately, then bound as typed SQL AST literals at execution; positional markers and unsupported types are rejected before admission.

B064.1 preserves each bound relation and alias when same-named tables occur in different schemas. B064.2 consumes Sparkless 4.15.0 public `toArrowBatches(max_rows=256, max_bytes=8 MiB)` batches and retains only the row/byte-limited prefix before JSON encoding; it scans the batches to report accurate total rows and truncation. This bounds retained result materialization, not Sparkless internal working memory. SQL JSON timestamps preserve the fractional precision represented by their Arrow units. B064.3 implements the bounded `INSERT INTO ... VALUES` and `INSERT INTO ... SELECT` append forms, with named scalar parameter binding, through `DeltaRsTableService` and its operation journal; other INSERT forms fail before mutation. See [B064 focused evidence](../../artifacts/conformance/B064-phase-0.1-review-fixes.md).

The supported output is `INLINE` `JSON_ARRAY`. It preserves field order/names, maps Arrow schema types to SDK type names/text, encodes non-null cells as strings, preserves nulls, and JSON-encodes nested arrays/maps/structs with string leaves. The local profile accepts `row_limit` from 1–10,000 and `byte_limit` from 1–8 MiB. A smaller explicit request limit returns the fitting row prefix and sets `manifest.truncated`; without an explicit limit, a result exceeding either hard cap fails with `RESOURCE_EXHAUSTED`. Results are split into indexed chunks of at most 1,000 rows. Active result payloads expire after 12 hours and share a 64 MiB workspace budget; the oldest expiry is closed first when storage is full. Expired or evicted payloads are removed, their statement metadata is retained, and polling reports `CLOSED`. A DELETE for a terminal statement closes retained result chunks while preserving its statement record; an active statement close returns a conflict. Named scalar parameter binding supports the selected NULL, STRING, BOOLEAN, integer, floating-point, DECIMAL, DATE, and TIMESTAMP types; other parameter types, request fields, timeout forms, `ARROW_STREAM`, `CSV`, and `EXTERNAL_LINKS` fail explicitly. No result link or arbitrary filesystem read is created. Current SQL routes through the B011.1 Sparkless/catalog/Delta services; a statement API 200/`SUCCEEDED` only represents a local observed execution.

### Implemented SQL warehouse identity and admission (B011.5)

Metadata schema 13 adds persistent SQL warehouse records, lifecycle events, and immutable statement admission history in the workspace SQLite database; schema 14 adds SQL statement requests/results; schema 15 stores typed parameter values; schema 16 permits notebook task kinds in job snapshots; schema 17 bounds, chunks, expires, and evicts inline statement results. The pinned Databricks SDK 0.153.0 loopback API supports create/get/list/edit/delete/start/stop for the serverless (`PRO` plus `enable_serverless_compute=true`), pro (`PRO` with the flag false/omitted), and classic (`CLASSIC` with the flag false/omitted) local profiles. It validates warehouse type/flag combinations, size, timeout, auto-stop, cluster bounds, duplicate names, and missing IDs; unsupported settings fail explicitly. Create starts metadata in `RUNNING`; edit returns a running resource as required by the pinned SDK waiter; stopped resources can be started again. A controlled-clock service hook stops idle warehouses without sleeping.

Admission follows the phase 0.1 limits: one active statement per warehouse, two active workspace-wide, and eight queued per warehouse. Queued statements are promoted in FIFO order when a slot is released. Stop, delete, configuration-generation changes, and idle stop invalidate queued leases immediately. Active leases remain `ACTIVE` while their worker is canceling or finishing, but the old warehouse generation fails admission/commit checks; capacity is released only at the actual statement terminal outcome. Restarted warehouses queue new work behind active old-generation workers, preserving the one-active-per-warehouse limit. Catalog creation also creates `default` and `information_schema`. The default catalog/schema and system schema are protected; registered tables prevent schema/catalog deletion. Only lowercase unquoted names and comments are accepted; unsupported SDK fields fail explicitly. The SDK test proves local transport and SQLite persistence across reopen, not Databricks workspace parity, permissions, SQL, or Delta data access. ### Selected native SQL row mutations (B019.2.1)

B019.2.1 implements one-table UPDATE and DELETE through the registered `DeltaRsTableService` and public `deltalake==1.2.1` `DeltaTable.update()` / `DeltaTable.delete()` methods. It binds a required WHERE predicate and simple assignment expressions against the current provider schema, passes the workspace journal's application transaction plus operation/fingerprint metadata to the same atomic provider commit, and returns exact affected-row metrics from Delta history. A fresh Sparkless 4.15.0 read observes those rows with the existing Arrow schema. A schema-version-18 journal migration preserves schema-17 operation records. Zero-row operations are persisted as `no_op` without advancing the Delta transaction sequence; provider failures are persisted as `failed` only after the base snapshot and application transaction are confirmed unchanged. Ambiguous outcomes remain uncertain and block later mutations. See [B019.2.1 evidence](../../artifacts/conformance/B019.2.1-sql-update-delete.md).

The selected UPDATE/DELETE subset requires one registered target and a WHERE clause. It accepts unqualified columns, primitive literals, arithmetic assignments, comparisons, boolean combinations, `IS NULL`, and literal-list `IN`. It rejects aliases, joins/FROM/USING, subqueries, functions, qualified expressions, RETURNING, ordering and limits before provider dispatch. UPDATE/DELETE and the bounded single-key MERGE below are local delta-rs/Sparkless results, not general Spark or remote Databricks parity.

### Selected native SQL single-key MERGE (B019.2.2)

B019.2.2 routes one registered target and one registered source table through `DeltaRsTableService.merge_rows()` and the pinned public delta-rs 1.2.1 `DeltaTable.merge()` API. The selected syntax has one qualified target-key/source-key equality, one unconditional matched `UPDATE`, and one unconditional unmatched `INSERT` with explicit source-column values for every target field. The target and source must have the same Delta schema; update/insert mappings must have matching Arrow types. Source key values must be non-null and unique. Unsupported actions, conditional clauses, duplicate keys, unknown columns, invalid targets, and schema/type mismatches reject before target journaling.

The provider receives a stable target snapshot fence, workspace application transaction, operation ID, and canonical source identity/version/data fingerprint. One native MERGE commit records exact inserted and updated metrics; replay reconciliation verifies those metrics against Delta history. A fresh Sparkless reader sees the exact committed rows and schema. Schema 19 admits the `sql_merge` journal mode and transactionally preserves existing schema-18 operation records. See [B019.2.2 evidence](../../artifacts/conformance/B019.2.2-sql-merge.md).

This slice does not implement source subqueries, multi-key or residual ON predicates, conditional clauses, deletes, star inserts, arbitrary expression mappings, differing schemas, or general Spark/Databricks MERGE parity.

### Selected SQL table description and Delta history (B019.2.3)

`DESCRIBE TABLE` reads the registered table's validated current Delta snapshot and returns one row per top-level field in provider schema order, with the exact Arrow result schema `col_name: string not null`, `data_type: string not null`, and `comment: string nullable`. Primitive, decimal, array, map, and struct Delta types render as Spark SQL type text. A comment is returned only when it is present in the committed Delta schema metadata; partition detail, extended/detail forms, and unrecognized schema types are unsupported.

`DESCRIBE HISTORY` delegates to the registered table service's public delta-rs history API and returns at most the latest 100 committed versions, newest first. Its fixed seven-column profile contains `version`, UTC millisecond `timestamp`, `operation`, string maps for `operationParameters` and `operationMetrics`, nullable `readVersion`, and nullable `engineInfo`. Numeric provider map values are represented as strings. No journal-only intent or estimated rows are substituted for Delta history. Identity, job/notebook/cluster, isolation, and other provider fields absent from the selected local history profile are not synthesized. `DESCRIBE EXTENDED`, `DESCRIBE DETAIL`, and a history `LIMIT` clause are rejected. Exact delta-rs 1.2.1 provider rows, schema, and operation order are recorded in [B019.2.3 evidence](../../artifacts/conformance/B019.2.3-sql-describe-history.md).

### Selected SQL version-as-of reads (B019.2.4)

The selected SQL profile accepts literal, non-negative integer `VERSION AS OF` selectors on registered Delta tables. The planner binds table identity and version, then removes the clause before rendering the Sparkless query. An isolated Sparkless session receives a version-pinned provider descriptor for each selected table; the SQL service also checks the requested snapshot through `DeltaRsTableService.read_table()` before engine dispatch. The SQL result schema and rows match both direct service reads and a Sparkless session pinned to the same table ID/version. Snapshot and file-retention failures raise `SnapshotUnavailableError`; there is no fallback to the current version. Historical snapshot sessions are read-only.

Timestamp selectors, negative, decimal, and string version values, malformed ranges, and parameterized selectors are unsupported. Future and vacuum-expired versions fail as unavailable. See [B019.2.4 evidence](../../artifacts/conformance/B019.2.4-sql-version-as-of.md).

The B019.2 mutation/history/snapshot contract is summarized in [the parent conformance report](../../artifacts/conformance/B019.2-sql-mutations-history-snapshots.md); child reports keep their specific limits and exact versions.

## Catalog model

Use SQLite migrations for workspaces, catalogs, schemas, table registrations, volumes, workspace objects, operation journals, jobs, task attempts, and capability/profile state. Table records include stable ID, fully qualified name, format, managed/external ownership, canonical location, creation metadata, and lifecycle state. Delta owns the physical schema and committed data version; a catalog cache must record its observed version.

Normalize identifiers with a documented Spark/Databricks profile. Preserve quoted names and display casing. Resolve current catalog/schema per session/request; enforce duplicate-name rules. Reject invalid traversal and resolve filesystem aliases/symlinks before ownership decisions. A single canonical physical location cannot be registered with conflicting ownership. Locks key on physical identity as well as table ID to prevent alias races.

Bootstrap an explicit default catalog/schema during workspace initialization. Tests create additional namespaces rather than relying on accidental defaults.

## Managed and external tables

Managed tables are real Delta directories under a UUID-based workspace storage path. External tables reference validated locations. `drop_table()` removes metadata for external tables and preserves their files. For managed tables it securely removes the direct UUID child under the workspace-owned `tables` directory before deleting metadata. If recursive deletion fails or the process stops before metadata removal, the registration remains and a repeated drop completes cleanup; an absent directory is safe to finalize. A pending or uncertain write blocks removal. Dropping a table removes its table-scoped operation journal rows in the same SQLite transaction as its registration. Rename changes catalog identity mapping and does not require moving data directories.

Creation with data proceeds through a journaled operation: reserve metadata identity, stage data, commit Delta, finalize metadata. Failure before commit cleans safe staging; failure after commit is reconciled from recorded operation identity. Table visibility must exclude incomplete creations until finalization or an explicit recovery state.

## File namespaces

Distinguish workspace files, DBFS paths, volumes, and raw table locations. Map `dbfs:/`, `/dbfs/`, `/Volumes/catalog/schema/volume/`, and local paths using a single path resolver. The mount root seen by the server can differ from the worker's root; pass explicit mapping, never string-replace arbitrary paths.

Use local files first. fsspec can support Python-facing backends, but Sparkless native readers require native-compatible URIs or a deliberate staging layer. Cloud URI support is not implemented merely by accepting an `s3://` or `abfss://` string.

## Table-service port

Proposed logical operations:

- `resolve(name, context) -> TableHandle`
- `drop_table(handle) -> None`
- `read_snapshot(handle, version?) -> schema + Arrow batches or native scan descriptor`
- `create/append/overwrite(handle, staged_input, write_options, operation_id) -> CommitResult`
- `update/delete/merge(handle, validated_expression_or_plan, operation_id) -> CommitResult`
- `history/describe/optimize/vacuum(handle, options) -> typed result`

`CommitResult` carries table identity, Delta version, physical schema, operation ID, and metrics. Record an input/options fingerprint for idempotency keys; reject reuse with different content. Empty tables, append schema mismatch, overwrite semantics, partition handling, and missing targets must be explicit tests.

Use Delta transactions and provider APIs. For retries after an uncertain response, reconcile an operation ID from provider transaction metadata/history before repeating. If the selected API cannot support reliable reconciliation, return an explicit uncertain-commit state and block automatic retries for that operation; do not advertise exactly-once behavior.

## Initial Delta envelope

Begin with local, unpartitioned tables and a verified primitive/nested-type subset; then add partitioning and schema evolution behind capabilities. Determine minimum reader/writer versions from actual fixtures rather than hardcoding guessed protocol numbers.

Reject unsupported table features before reads or writes. In particular, reading active Parquet files is not sufficient for deletion-vector semantics. Detect unsupported column mapping, deletion vectors, catalog-managed commits, and similar features even if simple scans appear to succeed. Every advertised feature must work through both Sparkless and SQL.

## SQL pipeline

1. Parse the declared Databricks/Spark dialect; preserve parameters as bound values.
2. Classify DDL, table mutations, queries, utility statements, and unsupported syntax using an AST.
3. Bind identifiers to the catalog, resolve request defaults, and check authorization/capabilities.
4. Route catalog changes to catalog services; table mutations to the Delta provider; queries to the declared engine.
5. Produce a unified schema/result stream and typed error envelope.

SQLGlot translation is useful for approved DuckDB execution. Do not use regex substitution for catalog names, external table locations, or predicates. A query can parse and transpile successfully but still differ semantically. Explicitly test null ordering, type coercion, integer overflow, decimal precision, dates/timezones, NaNs, duplicate columns, arrays/maps, and case resolution.

Prefer Sparkless for shared DataFrame/Spark SQL behavior. If DuckDB cannot evaluate an operation with the selected profile's semantics, reject it or route it by a predetermined capability plan before execution. Do not fall back after exceptions.

The bounded B019.1 semantic corpus currently verifies the frozen scalar case and grouped/empty aggregate cases against real local Delta plus Sparkless 4.15.0; see [B019.1.1](../../artifacts/conformance/B019.1.1-sql-scalar-cases.md) and [B019.1.2](../../artifacts/conformance/B019.1.2-sql-aggregate-cases.md). The observed local aggregate contract returns COUNT as Arrow `int32`, widens SUM over `DECIMAL(12,2)` to `decimal128(22,2)`, returns zero/null for COUNT/SUM over empty input, and raises `ValueError` for the selected invalid BIGINT cast. A bounded remote aggregate statement was rejected with `BAD_REQUEST`, so these are local Sparkless observations only and do not establish Databricks parity. C018 remains planned for broad Spark/Databricks semantic parity; the selected local corpus and profile cases do not establish that broader claim.

UTC-aware timestamp comparisons with naive literals and nested struct field SQL selection remain explicitly failing Sparkless 4.15.0 cases, tracked by [robin-sparkless #1714](https://github.com/eddiethedean/robin-sparkless/issues/1714) and [#1715](https://github.com/eddiethedean/robin-sparkless/issues/1715); no remote parity is inferred. ## Statement Execution API

Implement the pinned client's request/response shapes, warehouse identifiers, positional/named parameter forms where supported, wait/timeout behavior, result schemas, row encoding, chunk indices, cancellation, errors, and result retention. Separate statement lifecycle from query execution even for short queries. Reject result formats/dispositions not yet implemented.

Start with bounded JSON results; add Arrow/CSV and external result links only with actual retrieval and lifetime tests. Do not keep unbounded query data in module-global dictionaries. Result links must resolve to BrickHouse-owned artifacts, not arbitrary file reads.

## Consistency acceptance cases

B012.1's focused G1 report verifies that a Sparkless-created managed Delta table is visible through pinned-SDK SQL and fresh Sparkless sessions before and after a graceful local service/workspace restart. It compares the persisted table ID, canonical location, Delta version, schema and rows, and fetches a statement result created before restart. This is local execution evidence only. B012.2.1 adds empty-table and schema-mismatch proofs: typed empty managed tables retain schema without rows, and a mismatched append is rejected before the existing Delta version or rows change. B012.2.2 now verifies that external drops preserve files, stale service handles reject reads/writes, and an existing Sparkless session rejects later lookups and writes after table removal. B012.2.3 passes the G1 workflow under a macOS outbound-network sandbox that allows localhost only and guards Python imports/processes; see [the report](../../artifacts/conformance/B012.2.3-native-only-process-network.md). B012 G1 and boundary acceptance is complete for this local profile.

- A table written by a worker is read identically through SDK SQL and a fresh Sparkless session.
- Schema changes invalidate cached metadata; time-travel reads retain the requested version.
- SQL and DataFrame append share the same Delta history and preserve all committed rows.
- Restart during each create/commit/finalize phase produces a documented recoverable state.
- A retry of the same operation does not duplicate data; changed payload with the same key fails.
- External table drop preserves bytes; managed cleanup cannot delete outside the owned root.
- No advertised Delta feature can be bypassed through a different read/write surface.

## Preparation for later self-hosting

Preserve stable catalog/table/artifact identity separately from the local storage root. Current canonical local paths, ownership checks and journal evidence keep their existing scope. B048 records actual staging/path coupling; it does not replace local storage during 0.1. Emulator phases 0.2–0.9 retain identity, snapshot, protocol and mutation invariants in their own work.

After emulator stability, SH.1 enforces deployed caller identity for queries/results/mutations and SH.4 qualifies root mapping, snapshot access, native IO and bounded shared-storage/artifact transfer across hosts. Worker lease/generation validation must fence service commits without bypassing the Delta provider or uncertain-commit journal. Shared SQLite on an unverified network filesystem, accepted cloud URI strings or Python-only filesystem mocks cannot qualify this behavior. Restore/relocation requires explicit location mappings and managed/external ownership checks. See [document 18](18-self-hosted-platform.md).

## Future distributed-query sinks

[Document 19](19-sparkless-cluster-execution.md) requires provider-pinned scan fragments and typed bounded exchanges for a single query across hosts. Its future sink stages validated winning partition fragments and requests one native provider commit through this service. Distinguish stable logical write intent from fragment byte hashes, freeze accepted manifests for replay, and preserve uncertainty after a lost commit response. Current buffered Arrow writer callbacks and local delta-rs APIs do not automatically implement bounded multi-fragment commits; SC.0/SC.3 must prove that contract. No executor independently appends retried output or edits the Delta log. This optional track does not expand the local table envelope or existing emulator release gates.

## Reused parser/provider qualification

[Document 20](20-open-source-reuse.md) retains the declared delta-rs mutation provider and current Arrow envelope. SQLGlot is a candidate parser/AST tool, not semantic execution; DuckDB routes remain explicit and capability-selected. Optional dbt materializations and future UC/sharing/native-format adapters must reuse table IDs, snapshot/commit policy and ownership rather than create separate mutable copies. PyIceberg/Delta Kernel source availability does not qualify a new format, Delta feature or distributed manifest commit; B040/B041/SC.0 retain those decisions and tests.

The SQL COUNT type discrepancy was reproduced on published Sparkless 4.15.2 and reported as [upstream issue #1723](https://github.com/eddiethedean/robin-sparkless/issues/1723). DataFrame count produces LongType/int64; SQL COUNT produces IntegerType/int32. The release orders workflow uses native DataFrame aggregates and verifies BIGINT and DECIMAL(22,2) without output casts. The frozen SQL fixture remains an explicit local compatibility limit.
