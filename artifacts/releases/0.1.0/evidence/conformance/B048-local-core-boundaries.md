# B048 — Local-core architecture review

**Result:** passed · **Review scope:** implemented G1–G4 local workflows and their future deployment adaptation points · **Date:** 2026-10-21

## Conclusion

The reviewed local paths have one workspace catalog and table registration authority, one declared Delta mutation service, and distinct transport, domain, persistence, engine, and worker responsibilities. The tested G1–G4 paths reuse those authorities rather than creating a second catalog or committing data directly from SQL, Sparkless, or a worker. Stable domain IDs and durable operation/attempt records are distinct from local filesystem paths and process IDs.

One existing invariant violation was found: the diagnostics server could be bound beyond IPv4 loopback through direct library entry points even though it has no caller authentication. B048.1 fixed and tested that bypass. The remaining findings below are deployment gaps already assigned to SH.0 onward; this review adds no deployment implementation or public parity claim.

## Local identity, paths, and execution assumptions

- **Stable identity:** workspace UUID is persisted during bootstrap ([`lifecycle.py`](../../../../../src/brickhouse/workspace/lifecycle.py#L82)); catalog/schema/table registrations have durable identifiers ([`repository.py`](../../../../../src/brickhouse/catalog/repository.py#L303)); jobs, runs, task runs, and attempts have durable records ([`jobs/repository.py`](../../../../../src/brickhouse/jobs/repository.py#L75)); SQL statements and warehouses have durable IDs ([`sql/statements.py`](../../../../../src/brickhouse/sql/statements.py#L78), [`warehouse.py`](../../../../../src/brickhouse/compute/warehouse.py#L90)). Worker PID is volatile diagnostic state, not the identity of a run or attempt.
- **Workspace ownership:** [`WorkspaceOwner`](../../../../../src/brickhouse/workspace/ownership.py#L33) uses a nonblocking POSIX advisory lock on `.brickhouse-owner.lock`; migration and single-writer recovery assume a tested local POSIX filesystem. Windows and network filesystem locking are not claimed.
- **Local paths and staging:** managed tables reside below the workspace table root, while external registrations retain external canonical locations. [`StagingArea`](../../../../../src/brickhouse/tables/staging.py#L34) copies and verifies input under the workspace staging root. [`WorkspaceFileService`](../../../../../src/brickhouse/workspace/files.py#L56) confines API-managed source/file paths to the local workspace and rejects symlink/path escapes. These checks do not confine arbitrary Python file access.
- **Workers:** [`run_python_worker()`](../../../../../src/brickhouse/runtime/worker.py#L213) launches an explicit interpreter with a resolved working directory, minimal environment, `shell=False`, closed inherited descriptors, bounded pipes, and a POSIX session for descendant termination ([launch](../../../../../src/brickhouse/runtime/worker.py#L344)). The OS user still grants workers the host's ordinary file and network access; a fresh process is not a sandbox.
- **Internal worker channel:** [`WorkerServiceSession`](../../../../../src/brickhouse/runtime/worker_services.py#L38) uses a local socket pair and passes one descriptor to the child. A short-lived bearer is bound to a run/attempt, checked and revoked by [`WorkerAuthenticator`](../../../../../src/brickhouse/runtime/worker_auth.py#L177). This is per-attempt local service authentication, not caller authentication, remote-worker enrollment, or distributed fencing.
- **Secrets:** [`SecretProvider`](../../../../../src/brickhouse/runtime/secrets.py#L46) keeps values in process memory and grants scopes by local job ID. Values are sent to a worker through a bounded private pipe and exact values are redacted from captured output; grants are not principal-based or persistent across service restart.

Future storage adapters must preserve table IDs, ownership, snapshot/version semantics, and the single commit authority while explicitly mapping managed paths and external references. Future runtime adapters must preserve job/run/task/attempt identity and recovery semantics while replacing local interpreter/PID/signal/socket assumptions with tested service protocols. No generic backend was added as part of this review.

## Principal provenance and future enforcement points

The current HTTP server has no inbound authentication. Its compatibility SDK token is ignored as an authorization credential, and simulated current-user fields do not identify the process caller. Local deployment therefore assumes one trusted operator and strictly loopback access; the local APIs do not isolate separate users.

| Surface | Current local provenance and enforcement | Future enforcement point |
|---|---|---|
| HTTP/API | [`DiagnosticHandler`](../../../../../src/brickhouse/diagnostic_server.py#L61) dispatches routes without authenticating a caller. B048.1 ensures all server entry points accept only IPv4 loopback. SDK tokens and simulated client identities are compatibility data. | SH.1 must authenticate a principal at ingress, propagate it as application context, and enforce action/resource grants in domain services for every advertised route. |
| SQL | Statement/session IDs bind requests to local warehouse execution and persisted results; they do not bind a session to a caller identity ([`SqlStatementHttpApi`](../../../../../src/brickhouse/api/statements.py#L61), [`SqlStatementExecutionService`](../../../../../src/brickhouse/sql/statements.py#L497)). | Enforce principal ownership at session creation, statement submission/cancel, warehouse admission, and statement/result fetch/close. |
| Jobs/workers | Job IDs and scopes are local resource identifiers. A scoped attempt token authenticates only the worker-to-parent private service channel; it does not prove who submitted a job or restrict arbitrary Python host access. | SH.1 maps authenticated job owners to run/attempt/output grants; SH.3 establishes the actual code isolation boundary; SH.4 adds enrolled worker identity and fenced attempt leases. |
| Files | Workspace file APIs enforce local root and symlink boundaries but expose a shared workspace namespace to any process that can reach the loopback service. | Authorize upload/read/overwrite/delete by principal and workspace path; test denial and symlink cases through authenticated transport. |
| Secrets | Values are memory-only; explicit job-ID scope grants control the local helper API, not an authenticated owner. | Enforce principal/service identity at secret grant and retrieval, protect durable credentials, and define rotation/restart/recovery in SH.1. SH.3 must prevent code from reading unauthorized secrets through host access. |
| SQL results and worker output | Durable statement IDs and job/run/attempt IDs retrieve persisted results/output; no principal ownership check exists. | Apply the same principal policy to result manifests/chunks, worker output and logs at read, close, expiry and deletion boundaries. |

## Findings and disposition

1. **Resolved before release:** direct diagnostics server entry points could bind an unauthenticated server to non-loopback hosts. B048.1 now validates at the direct factory, serving function and CLI boundary; [its report](B048.1-loopback-bind-boundary.md) records 13 focused passes, Ruff, mypy and diff evidence.
2. **Retained for SH.1:** no inbound principal authentication/authorization, durable deployed secrets, or per-user ownership exists. Adding local permission labels would not close this gap and is outside 0.1.
3. **Retained for SH.3:** workers execute arbitrary Python with the local OS user's ordinary access. Process separation and import compatibility are not a sandbox.
4. **Retained for SH.4:** local PID, signal handling, inherited descriptors, socket pairs, workspace paths, SQLite, and POSIX locks are not remote leases, shared storage, or multi-host fencing.
