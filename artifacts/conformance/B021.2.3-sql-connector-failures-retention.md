# B021.2.3 — SQL connector failures, cancellation, and method limits

Date: **2026-10-21**. Task: **done**. B021 and B021.2 are complete for the documented local REST/SEA connector subset; C031 remains **partial**.

## Profile and evidence

The local-only conformance test uses the hash-verified Python 3.11 distributions recorded by B045: `databricks-sql-connector==4.6.0` (SHA-256 `9f2128592052d3aadb7a3c46df0a8ef414402ec6ea7a0fdb8490da737fe43cdc`), `databricks-sql-kernel==1.1.0` (SHA-256 `8d7bf7aa002dc2f4864170f1e9185ba10fdf5460efb114269ec9337b084bd501`), and `pyarrow==23.0.1`.

The actual connector ran against an ephemeral BrickHouse workspace over strict loopback HTTPS with a trusted temporary CA and synthetic Bearer token. The child environment did not contain `DATABRICKS_TOKEN` or `DATABRICKS_HOST`; no `.env`, personal workspace, cloud compute, Spark, or JVM was used. The test invokes the synchronous SEA client because it exposes the public `Cursor.cancel()` method; the earlier kernel session lifecycle and one named-parameter result case remain covered by the same fixture.

## Observed behavior

- `SELECT * FROM b021_missing_table` raised connector `ServerOperationError`. The local endpoint returned HTTP 200 with statement state `FAILED`, error code `BAD_REQUEST`, SQL state `42000`, and no result or manifest. The connection then executed `SELECT 7 AS answer` and fetched `[[7]]`.
- `cursor.catalogs()` sent `SHOW CATALOGS` and raised `ServerOperationError` for the explicitly unsupported local SQL operation. Its failed response carried no result or manifest; no empty catalog list was fabricated.
- With the released connector's default `ignore_transactions=True`, `connection.rollback()` raised its documented `NotSupportedError` locally and sent no SQL request. This is a driver method limitation, not a BrickHouse rollback implementation.
- A regular synchronous query waits up to the connector's fixed `10s` before publishing its command ID. The fixture held the local query before engine execution, waited until the connector published that ID, then called public `cursor.cancel()` from another thread. The connector sent `POST /api/2.0/sql/statements/{id}/cancel`; BrickHouse returned HTTP 200 and a subsequent GET observed terminal `CANCELED` without a result or manifest.
- For that canceled synchronous command, connector 4.6.0 raised `ProgrammingError: Invalid result format` while converting the canceled response into a result set. It did not return fabricated rows. This is recorded as a client-visible limitation; no broader cancellation-parity claim is made.
- The connector closed a terminal result and both connector sessions through DELETE requests. The existing SQL API regressions verify a closed result reports `CLOSED` while preserving statement metadata.
- Local retained results have a 12-hour expiry and a 64 MiB workspace-wide active-result budget with oldest-first eviction. The expiry regression verifies that payload chunks are removed while history remains; the eviction regression verifies the oldest result becomes `CLOSED` and its chunks are unavailable.

`cursor.schemas()`, `tables()`, and `columns()`, kernel Arrow-stream/LZ4 query results, Thrift, remote Databricks behavior, and broader DB-API semantics remain unqualified. The connector's default kernel query request (`INLINE_OR_EXTERNAL_LINKS`, `ARROW_STREAM`, `LZ4_FRAME`) is explicitly outside the local result profile.
