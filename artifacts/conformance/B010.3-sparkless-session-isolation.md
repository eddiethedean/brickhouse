# B010.3 — Sparkless session isolation and compute profiles

Date: **2026-10-20**. Result: **passed for the selected internal session/profile contract**.

## Verified behavior

The internal Sparkless factory consumes `ResolvedTaskContext` through `open_for_execution()` and creates a fresh session with that context's validated settings and profile identity.

- A serverless task context resolves to `serverless-local-v1`, ANSI enabled, and UTC. The internal session reports that profile and those effective settings.
- A classic-standard task context resolves only through the explicit local runtime alias `spark35-local-v1`. The session receives the context's explicit ANSI and timezone values. Classic ANSI/timezone defaults are not inferred: a context without both values fails with `UnsupportedSparklessConfigurationError`.
- Two live sessions remain independent across different registered namespaces, session configuration, temporary views and distinct `functions.udf` callables. Both UDF results retain the declared `LongType` schema and return their own expected values.
- The existing adapter still rejects unreviewed Spark settings, unsupported profiles, and access from a non-owning thread.
- `close()` detaches and stops the native session, then clears BrickHouse's native-session/facade references on the owner thread. The owner-thread close test asserts the native handle has been released; after this fix the full suite completed without the previously observed PyO3 cross-thread-drop warning.

The tests keep both native sessions open in the same owner thread and exercise them in turn. Sparkless sessions are owner-thread bound, so this is evidence for coexisting isolated sessions, not parallel query execution. The UDF case covers two distinct callable expressions; it does not qualify arbitrary Python UDFs, a session-scoped SQL `CREATE FUNCTION` registry, pandas UDFs, Spark Connect analysis timing, or cross-thread execution.

## Limits

This is an internal local adapter, not a public session API or proof of end-to-end serverless/classic workload compatibility. It covers serverless defaults and one classic-standard local runtime/configuration combination. It rejects classic settings when required ANSI/timezone values are absent and rejects all unmapped runtimes. Classic-dedicated settings, other runtimes, Databricks reference parity, and Sparkless sessions in job/notebook workers remain unverified. The current three-key setting allowlist is intentionally narrower than Databricks configuration surfaces.
