# B015.1.3 — Authenticated registered-table reads in worker sessions

Date: **2026-10-21** (America/New_York). Result: **passed for the selected local worker profile**.

## Behavior

Managed workers with the existing attempt-authenticated parent service can resolve a table name only through BrickHouse's catalog and `DeltaRsTableService`. The parent returns the table ID, canonical registered location, Delta schema JSON, provider identity, and the exact committed snapshot version. The worker validates that descriptor through Sparkless 4.14.1's public `ExternalTableDescriptor` API and attaches it with `SparkSession.set_external_catalog_provider()`.

`SparkSession.table()` and read-only SQL now use the same session-scoped provider. Both read the committed local Delta rows in the worker process. Missing names, unsupported identifiers, and unregistered Delta paths fail explicitly. Worker DataFrame writes and SQL mutations remain blocked, so registered-table mutations continue to use BrickHouse's common table service.

The attempt socket, run ID, and attempt ID are authenticated before catalog resolution. Plain Python workers or workers without that service cannot access registered tables through the facade. The parent and child still use separate workspace processes; the descriptor is bounded by the existing 64 KiB worker-message limit.

The new pinned-SDK loopback job read a real registered Delta table through both `spark.table()` and `spark.sql()`. It rejected a missing table and a real but unregistered Delta path, rejected DataFrame and SQL writes, and left the committed table at version 0. Ruff check/format passed; strict mypy passed for the changed worker/session/job modules.

## Sparkless feature check and limits

The published Sparkless 4.14.1 public external-catalog API supplies the complete synchronous, version-pinned descriptor contract needed here. **No new Sparkless issue was warranted for B015.1.3.** Active SQL/DataFrame cancellation and bounded Arrow batch/stream export remain tracked in [#1705](https://github.com/eddiethedean/robin-sparkless/issues/1705) and [#1706](https://github.com/eddiethedean/robin-sparkless/issues/1706). A later broader review identified the separate structured provider-error gap and filed [#1707](https://github.com/eddiethedean/robin-sparkless/issues/1707); that does not affect the registered-table read behavior verified here.

This does not add `delta.tables.DeltaTable`, worker table mutations, Spark Connect compatibility, remote workspace access, or broad serverless/classic workload parity. Those remain separate tasks and qualification gates.
