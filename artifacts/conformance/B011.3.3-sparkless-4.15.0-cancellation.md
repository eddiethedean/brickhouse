# B011.3.3 — Sparkless 4.15.0 cancellation contract

Date: 2026-10-21

## Published contract

The published `sparkless==4.15.0` macOS arm64 wheel is SHA-256
`2cdb3dccaac9ee1da4bf47d17fae8457eb9564923ab0568e5885ed22ce93ba4f`.
Its public Python surface exports `SparklessCancelledError`, exposes
`DataFrame.cancel()`, and provides `SparkSession.cancellation_handle()` with
`cancel_all_active_actions()`. The handle is documented as thread-safe. The
release changelog records cooperative SQL/DataFrame cancellation, bounded Arrow
batch export, and structured provider callback errors. Upstream PR #1708 merged
the cancellation contract and closes issue #1705.

## Local release probe

Installed the downloaded wheel into a temporary target outside the repository's
developer environment. With `DATABRICKS_TOKEN` and `DATABRICKS_HOST` unset, the
probe ran `SparkSession.range(10_000_000).toArrow()` on a worker thread, then
requested cancellation through a session cancellation handle from the control
thread. The handle reported two signaled active actions; the worker terminated
with `SparklessCancelledError` and returned no rows. The probe used no workspace,
Databricks account, or table write.

## BrickHouse statement conformance

BrickHouse now pins Sparkless 4.15.0 in its developer lock and adapts the public
cancellation handle to the SQL statement lifecycle. SDK cancellation and
`on_wait_timeout=CANCEL` requests do not mark an active statement terminal by
themselves. Active leases remain held until the query worker reports
`SparklessCancelledError` or reaches a safe pre-execution/commit outcome. A
warehouse generation change fences future commits while the old active lease
continues to consume workspace capacity until execution terminates. Queued work
is invalidated immediately.

The SQL service uses an explicit commit fence for DDL and CTAS. A cancellation
after CTAS has committed does not discard or relabel that write: the SDK reports
success and the committed Delta table remains readable. SELECT completion and
cancellation races preserve the actual engine outcome.

The focused regression command was:

```sh
env -u DATABRICKS_TOKEN -u DATABRICKS_HOST PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 \
  /tmp/brickhouse-b0171-env/bin/python -m pytest -q \
  tests/unit/test_sql_statement_service.py \
  tests/unit/test_sql_statement_api.py \
  tests/unit/test_sparkless_engine.py \
  tests/unit/test_sql_warehouse_service.py
```

It passed **51 tests** with Sparkless 4.15.0, databricks-sdk 0.153.0 against
loopback only, delta-rs 1.2.1, and PyArrow 23.0.1. Coverage includes active
native cancellation, queued cancellation, actual wait-timeout cancellation,
warehouse-stop cancellation, lease retention until terminal outcome, late
cancellation after SELECT completion, cancellation after committed CTAS, and
admission promotion/cleanup, including a stale-generation active lease that
continues to count against restarted-warehouse capacity. Ruff check, Ruff format
check, and strict mypy for the changed runtime modules passed. Databricks
credentials were unset. No
personal workspace, cloud compute, Java, Spark driver, or remote execution was
used.

This establishes the selected local SQL cancellation contract, not remote
Databricks parity. B011.4 separately records BrickHouse's request limits,
chunking, expiry, and retention policy. Sparkless 4.15.0's bounded Arrow batch
API has not been integrated into BrickHouse query result materialization.
