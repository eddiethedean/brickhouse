The connector v4.6.0 release notes describe the kernel as stable and note that a Thrift connection can recover to kernel after SQLSTATE `KP001`; the same-tag connection-parameter page still labels the kernel early access. Treat this as an upstream documentation inconsistency. Set `use_kernel=True` or `False` explicitly in every capture and local client test so a backend switch cannot silently merge the two transport corpora.

B045 reinstalled the exact 4.6.0/1.1.0 wheel pair and verified both wheel hashes in a local HTTPS session-open capture. This capture does not establish query compatibility.

## Semantic and storage profile

- Initial local target: capability profile `spark35-local-v1`, currently using published Sparkless `4.13.4` with its `compat=3.5` behavior. This is a local PySpark-semantics target only; it is not an observed Databricks Runtime or SQL Warehouse profile.
- Initial B003 source inspection used `eddiethedean/robin-sparkless` commit `b73067252abd0720ea91ac447bfd3ce027e96a88`, package version `4.13.3`. The current release is tag `v4.13.4`, commit `34049bde128931e21bf34b761cfa10007d62af5e`; its tested CPython 3.11 macOS arm64 wheel hash and B004.2 results are recorded in the conformance report.
- Delta provider selected by B004.3: Python `deltalake==1.2.1`; B004.2 typed cross-read passed with Sparkless 4.13.4 and PyArrow 23.0.1, including exact `decimal(12,2)`. The prior 4.13.3 regressions tracked in #1683, #1684, and #1686 pass their local release repros. B004.3 verified default protocol reader 1/writer 2 and local transaction lookup/checkpoint/crash reconciliation. Advanced Delta features, cloud storage, external concurrency, and BrickHouse provider integration are not established.
- Databricks account, workspace URL, workspace runtime, warehouse version, and enabled account features are **not observed**. The owner reports a new account with no workspace or compute set up. `DATABRICKS_TOKEN` is present in ignored local `.env`; host, account ID, CLI profile, compute, and scratch namespace are absent. No remote request has been made.

## Minimum workflows and fixture provenance

1. **SDK:** use explicit `host` and local auth configuration targeting loopback; create/list/get/delete a catalog and schema; upload a synthetic Python file; submit, poll, and retrieve bounded job output; submit SQL and read results. Tests use a local compatibility token and do not load `.env` or discover user profiles.
2. **CLI:** target the same explicit loopback service and perform workspace import plus Python-job submit/poll/output. Verify the CLI's selected auth profile and host are explicit in the test process.
3. **Terraform:** pin both Terraform Core and the Databricks provider; B020.2 covers the selected workspace-file and existing-cluster Python-job resources against an isolated local BrickHouse workspace and confirms state refresh and cleanup. B020.4 separately covers compute/warehouse resources. Do not provision cloud resources for these compatibility workflows.
4. **SQL connector REST/kernel:** use TLS verification and explicit local host, HTTP path, auth, and `use_kernel=True`; cover parameters, result schema/pages, errors, cancellation, and expiration.
5. **SQL connector Thrift:** retain a separate, non-0.1 profile with explicit `use_kernel=False`; do not claim it until a real local Thrift server and its metadata/session/result contract pass.

The golden `orders` dataset and local workspace examples are synthetic project fixtures described in [the 0.1 release contract](../../docs/plan/16-phase-0.1-initial-release.md); they are not copied from a Databricks account. Once a permitted account workspace exists, a separately named manual probe can capture one behavior with exact client/profile provenance and sanitized output. Such a capture informs local expected results but cannot by itself support a BrickHouse capability claim. Ordinary tests remain local.

## Consequences

- B005.1 is complete as artifact/version research. B005.2–B005.5 and the B005 parent remain open until their workspace, capture, isolation, and workflow criteria have evidence.
- B020.2 selected and proved the workspace-file and existing-cluster Python-job lifecycle. B020.4 owns Terraform cluster and warehouse resources. B021 owns implementation-level SQL REST/kernel behavior. Default Thrift stays outside the initial supported surface.
- Revalidate release pins immediately before implementation and publication. A version pin in this matrix is not a dependency lock, compatibility result, or license audit.
