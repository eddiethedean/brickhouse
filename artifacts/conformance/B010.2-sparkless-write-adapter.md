# B010.2 — Sparkless writes through the Delta table service

Date: **2026-10-20**. Result: **passed for the selected internal local write contract**.

## Implemented behavior

The internal `SparklessSessionFactory` now connects the published Sparkless 4.14.1 Python provider to BrickHouse's `DeltaRsTableService` for registered local tables.

- `SparklessSession.create_managed_table()` converts a Sparkless DataFrame to Arrow and creates its registered managed Delta table through the service. The caller supplies the durable operation ID. Repeating the same operation and payload returns its recorded commit; reusing that ID for different input fails.
- `DataFrame.write.format("delta").mode("append"|"overwrite").saveAsTable(name)` delegates existing registered names through Sparkless' public write callback. The callback pins the request to the descriptor's Delta version, and the table service rejects a stale descriptor while holding its table mutation lock.
- `SparklessSession.write_path(dataframe, location, mode, operation_id=...)` writes through the same service only when `location` resolves to a registered local table. It uses a caller-supplied operation ID.
- Native `DataFrameWriter.save(path)`, insert writers, `DataFrameWriterV2`, writer options, partitioned writes, unregistered names/paths, and SQL statements with mutation or multiple-statement entry points fail explicitly. Existing-table `saveAsTable()` requires explicit append or overwrite mode.

The DataFrame writer callback generates an operation ID because Sparkless 4.14.1's public write-request contract has no operation-ID field. Caller-controlled replay IDs remain available through the explicit create and path methods. SQL and job-worker execution do not use this adapter, and `Workspace.session()` is not exported.

## Limits

The adapter is internal. It does not establish a public `Workspace.session()` API, SQL DML, job-worker Spark/Delta effects, Databricks parity, cross-process Delta coordination, or support for schemas outside the tested envelope. The native Sparkless callback buffers the full Arrow IPC payload before the adapter's 8 MiB / 100,000-row checks; those checks do not bound peak DataFrame materialization memory. When a callback-generated operation has an uncertain provider outcome, the journal blocks a blind follow-up write, but the Sparkless callback contract does not let the caller supply that same operation ID for explicit replay. Sparkless also wraps arbitrary callback exception types without retaining their structured category/context; this broader provider contract is tracked by [upstream issue #1707](https://github.com/eddiethedean/robin-sparkless/issues/1707).
