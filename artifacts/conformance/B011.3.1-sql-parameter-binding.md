## Verified behavior

The pinned SDK submits named `:marker` parameters to the local API. BrickHouse validates marker/value correspondence and supported types before creating a statement or acquiring warehouse admission. Supported values are NULL, STRING (the default when type is omitted), BOOLEAN, TINYINT/BYTE, SMALLINT/SHORT, INT/INTEGER, BIGINT/LONG, FLOAT, DOUBLE, DECIMAL(p,s), DATE, and TIMESTAMP. Integer ranges and decimal precision/scale are checked; timestamp offsets are normalized to UTC. Positional markers, duplicate/missing/unused names, invalid values, complex types, more than 100 parameters, and parameter payloads over 1 MiB are rejected.

Values remain separate from original SQL in workspace metadata schema 15, so pending parameterized statements survive workspace reopen without rewriting their stored SQL text. At execution, BrickHouse replaces marker nodes in a parsed SQL AST with typed literal nodes and renders them with Sparkless-compatible quote escaping. The loopback tests execute real Sparkless queries over local Delta data, verify decimal and boolean filters, NULL, DATE/TIMESTAMP/DOUBLE output, and return an injection-shaped string as data while preserving the source table. A pending parameterized query succeeds when polled after reopening the workspace.

This is a contained local adaptation: Sparkless 4.14.1's public `SparkSession.sql` accepts only a query string and has no argument-binding API. BrickHouse does not use raw string replacement or claim server-side prepared execution. Parameter values are persisted as request data and are subject to local workspace file access controls.

The reference API contract is documented in the [Databricks Statement Execution API](https://docs.databricks.com/api/statement-execution/v1/statement-execution): named markers, optional types defaulting to STRING, omitted values representing NULL, and no positional markers.

## Limits

Only the listed scalar types are supported. Complex parameter types, positional markers, Databricks runtime semantics outside the local Sparkless profile, hybrid wait-timeout behavior, and active-query cancellation are not implemented here. Sparkless's missing active SQL/DataFrame cancellation contract is tracked in upstream [#1705](https://github.com/eddiethedean/robin-sparkless/issues/1705).
