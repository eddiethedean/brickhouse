# B020.4 — Terraform classic compute and SQL warehouses

**Date:** 2026-10-21  
**Scope:** Local lifecycle conformance for one classic cluster and the serverless, Pro, and classic SQL warehouse resource profiles.

## Pinned clients

- Terraform Core `1.16.6` (`darwin_arm64`).
- `databricks/databricks` provider `1.137.0`, pinned by [the checked-in lockfile](../../tests/fixtures/terraform/1.137.0/.terraform.lock.hcl). The provider's [cluster resource implementation at v1.137.0](https://github.com/databricks/terraform-provider-databricks/blob/v1.137.0/clusters/resource_cluster.go) reads pin status from `clusters/list?filter_by.is_pinned=true` and permanently deletes managed clusters through the permanent-delete API.
- Databricks SDK `0.153.0` for the local cluster API checks; Python `3.11.15`.

## Implemented local profile

The Terraform fixture applies one `databricks_cluster` and three `databricks_sql_endpoint` resources. The warehouse profiles are `PRO` with `enable_serverless_compute=true`, `PRO` with the flag false, and `CLASSIC` with the flag false. IDs and the selected settings persist in the local SQLite metadata service. All infrastructure lifecycle labels remain simulated; no cloud compute is provisioned.

Terraform refreshes clusters by asking for pinned clusters even when a resource uses the default `is_pinned=false`. BrickHouse returns an empty pinned-only page because cluster pin/unpin is outside this profile, and its selected cluster response explicitly says `is_pinned=false`. The provider's direct permanent-delete call now follows the documented Databricks behavior by terminating an active local cluster before removing its metadata ([API reference](https://docs.databricks.com/api/clusters/v2/permanent-delete-cluster)).

## Conformance evidence

The opt-in integration test applies, reads, updates, refreshes, and destroys the selected resources against an ephemeral loopback server. It verifies stable IDs, exact warehouse type/flag combinations, cluster settings, an invalid classic/serverless combination that leaves persisted state unchanged, and not-found results after destroy. Focused SDK tests also verify pinned-filter behavior, cluster lifecycle state, and direct permanent deletion of an active cluster.

Command run with the Databricks token and host unavailable to the test process and only a synthetic token/loopback host passed to Terraform:

```text
env -u DATABRICKS_TOKEN -u DATABRICKS_HOST \
  BRICKHOUSE_TERRAFORM=/tmp/brickhouse-terraform-1.16.6/terraform \
  BRICKHOUSE_TERRAFORM_PLUGIN_CACHE=/tmp/brickhouse-b0204-provider-cache \

  tests/unit/test_compute_api_sdk.py \
  tests/unit/test_sql_warehouse_service.py \
  tests/integration/test_terraform_v1_16_6_provider_1_137_0.py::test_terraform_v1_16_6_compute_and_warehouse_profiles
8 passed
```

## Limits

- This proves the selected resource metadata and lifecycle contracts only. Compute and warehouse allocation, state, sizing, and cleanup are simulated, and this does not establish remote workspace authentication or Databricks workload compatibility.
- The provider's read-only computed `odbc_params` field remains unavailable because BrickHouse does not implement an ODBC listener. After warehouse updates and refresh, Terraform reports a residual plan containing only that computed field for the three warehouse resources. No connection endpoint was fabricated. The selected configurable settings and persisted state do refresh correctly, but a clean no-drift plan for these warehouse resources is not claimed.
- Cluster pinning, JDBC/ODBC connections, warehouse SQL execution through ODBC, and broader Terraform resources remain unsupported or unverified.
