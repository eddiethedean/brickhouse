## Concurrent-write and replay result

`tests/unit/test_sparkless_engine.py::test_concurrent_sql_and_dataframe_appends_serialize_location_aliases_and_replay` creates two workspace catalogs that register the same table name at the same physical Delta location through different paths. The registrations have different table IDs and the test confirms their locations canonicalize to the same path.

The DataFrame route uses `SparklessSession.write_path()` to append row `20`. The SQL route uses a local `MERGE` with an unmatched insert to append row `10`. The test holds the DataFrame writer at its real `write_deltalake` call after it has acquired the table mutation lock. While that write is held, the SQL route captures target version 0 and reaches the mutation boundary. SQL does not enter its native MERGE while the DataFrame commit owns the location lock. Once released, the DataFrame commits version 1; SQL's original version-0 attempt raises `StaleTableSnapshotError` before any journal row is created. One caller retry with the same SQL operation ID commits version 2.

Both routes are replayed with their original operation IDs. Each replay returns the original commit version and causes no provider dispatch. The test observes exactly two native commit dispatches, never more than one active at once, one Delta history entry per operation ID, and final rows `[0, 10, 20]`. The independent workspace journals each retain a `COMMITTED` record with its own operation and commit version.

This evidence is limited to same-process writers: the mutation lock serializes canonical-location aliases across workspace contexts in this Python process. It does not establish cross-process, cross-host or network-filesystem locking, and the SQL append in this fixture is MERGE's `WHEN NOT MATCHED INSERT`; it does not qualify a standalone SQL `INSERT` statement.
