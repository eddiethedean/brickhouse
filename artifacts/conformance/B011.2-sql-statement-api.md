# B011.2 — SQL statement API and JSON results

## Scope

Implemented the pinned Databricks SDK Statement Execution API 2.0 request path against the local diagnostic server. `WorkspaceClient.statement_execution` can submit a statement, receive a durable statement ID/state, poll it, and fetch inline result chunk zero. The selected SQL executor plans through SQLGlot, reads registered Delta tables through a fresh Sparkless session, and routes supported DDL through the shared catalog and Delta services.

Omitted `wait_timeout` runs the statement before returning. `wait_timeout="0s"` returns `PENDING`; the first status/result poll claims the request and runs it locally. Successful and failed terminal states and JSON results persist in workspace metadata. A service restart preserves terminal results and marks any previously `RUNNING` request failed without replaying potentially effectful SQL.

The API returns `INLINE` `JSON_ARRAY` with field names, API type names/type text, decimal precision and scale, nulls, and string-encoded scalar values. Nested arrays/structs/maps are JSON strings with string-encoded leaves. The retained [B005.3 Databricks SQL report](B005.3-databricks-reference-sql.md) and [sanitized fixture](../../tests/fixtures/oracles/databricks/B005.3-sql-literals.json) informed the literal encoding checks; they remain reference evidence and are not runtime tests.

## Limits

- At the B011.2 slice boundary, warehouse IDs resolved to running local metadata but leases were not yet bound to execution. B011.6 now implements that integration; see [its conformance report](B011.6-sql-warehouse-statement-binding.md).
- Results are limited to 10,000 rows and 8 MiB of encoded row data. The initial profile exposes one inline chunk. Full row/byte-limit request semantics, result expiry/cleanup, and multi-chunk behavior remain with B011.4.
- Bound parameters, timeout/cancellation behavior, and `on_wait_timeout` are not implemented; unsupported request fields and timeout forms fail explicitly (B011.3).
- `ARROW_STREAM`, `CSV`, and `EXTERNAL_LINKS` are rejected before statement creation.
- The loopback API does not authenticate or authorize callers. Local SDK compatibility does not establish remote Databricks parity.
- SQL compatibility is limited to the B011.1 planner/executor corpus; engine errors become persisted `FAILED` results and are not retried with DuckDB or a remote engine.
