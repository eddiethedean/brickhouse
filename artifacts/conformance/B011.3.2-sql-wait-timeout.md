## Verified behavior

The pinned SDK and local API exercise omitted `wait_timeout` (10 seconds), explicit `0s`, and valid `5s`–`50s` waits with `on_wait_timeout=CONTINUE`. An immediate request returns the initial persisted `PENDING` response. A request that exceeds its wait returns its actual persisted `RUNNING` state and statement ID; the managed continuation completes after the client receives that response. A controlled 5-second timeout test confirms the query executes exactly once and polling returns its terminal result.

Continuations belong to the SQL service and are retained until completion. Atomic statement claiming prevents polling and continuation from dispatching the same SQL twice. Server shutdown cancels work that is still queued and waits for active native SQL calls to finish before releasing workspace ownership. A pending statement restored after reopening resumes from its persisted SQL and typed parameter data.

Malformed/out-of-range waits and unsupported `on_wait_timeout` values are rejected before statement creation or admission. `on_wait_timeout=CANCEL` returns an explicit unsupported-operation response before admission because Sparkless has no active-query cancellation contract. No query is reported canceled while it may still be running.

## Limits

The API supports `CONTINUE` when a positive wait expires. Explicit statement cancellation and `on_wait_timeout=CANCEL` remain blocked on Sparkless's public active-query cancellation contract tracked in [upstream issue #1705](https://github.com/eddiethedean/robin-sparkless/issues/1705). Shutdown therefore waits for active engine calls rather than closing their workspace context underneath them. Result chunks and expiry remain B011.4 work.
