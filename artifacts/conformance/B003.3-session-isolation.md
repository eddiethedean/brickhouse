# B003.3 — Sparkless session and callback delivery risks

## Probe identity

- Sparkless repository: `eddiethedean/robin-sparkless`
- Source revision: `b73067252abd0720ea91ac447bfd3ce027e96a88`
- Package: Sparkless 4.13.3
- Environment: isolated local build in `/tmp/brickhouse-b0032-probe`; CPython 3.11.14, macOS ARM64, delta-rs Python package 1.2.1, PyArrow 23.0.1
- Probe: [B003.3-session-isolation.py](../probes/B003.3-session-isolation.py)
- No Databricks host, token, network service, or remote compute was used.

## Observed behavior

The probe creates a base session, then creates two child sessions sequentially on the same Python thread. Each child gets its own config mutation and a temp view with the same name but a different one-row DataFrame. SQL through each session returns its own row (`[(1,)]` and `[(2,)]`), and each session reports its own config value (`left` and `right`). An unresolved SQL column raises `SparklessError` with an `unresolved_column` diagnostic; the operation does not return fabricated data.

This demonstrates config and temp-view isolation for sequential sessions used on the creating thread. It does not establish concurrent session safety, UDF isolation, cross-thread activation, cancellation, or external-provider callback behavior.

A separate attempted `ThreadPoolExecutor` probe moved an existing `SparkSession` object to a worker thread. PyO3 panicked with `sparkless_native::PySparkSession is unsendable, but sent to another thread`. The binding is explicitly declared `#[pyclass(unsendable)]`. BrickHouse must not transfer a Sparkless session object between Python threads at this revision. Jobs already have a fresh-child-process target; any in-process service design must keep a session on its owner thread or require a tested upstream ownership model.

The session lifecycle is also thread-contextual: `newSession()` registers the new object on the current thread's active-session stack, while the DataFrame `createOrReplaceTempView` convenience method resolves that active session. Interleave session creation and implicit view registration and a DataFrame can bind to the wrong active session. The probe therefore creates/registers each view immediately after making that session active. A production adapter needs explicit session context for every operation.

## Callback, GIL, reentrancy, failure, and cancellation contract

- **Ownership:** the workspace owns the catalog/provider; a session owns its namespace, temp-view state, and provider context; Rust plans may retain only Rust-owned table descriptors/snapshot identity, never a borrowed Python session or request model. A descriptor must identify table ID, canonical location, schema, observed Delta version, and permission context.
- **Thread/GIL:** the inspected PyO3 session is unsendable. The binding methods execute synchronously through PyO3 and the inspected module has no `detach`/`allow_threads` path for these operations. No callback trait currently exists. Any future Python callback must run on the owning Python thread with the GIL held; this is a proposed constraint, not a tested hook. Do not use `PyObject` as a value captured by the `Send + Sync` engine traits.
- **Reentrancy/locks:** callbacks must not run while an engine-wide/session catalog mutex is held. Resolve into an owned descriptor, release internal locks, invoke a provider, then revalidate the snapshot/version before applying a mutation. A callback that calls Sparkless recursively must either be prohibited with a clear error or be covered by explicit reentrancy tests.
- **Failures:** preserve the provider's typed category and operation/table/version context across the Rust/Python boundary. Current PyO3 conversion turns many engine errors into `SparklessError` strings; BrickHouse must not branch on rendered diagnostics. Provider failures must remain failures and must not silently fall back to Sparkless local storage.
- **Cancellation:** no job cancellation token/API or cooperative interrupt path was found in the inspected Rust/Python interfaces. Do not advertise in-process cancellation. The minimum future contract is a cancellation token observed between execution batches and before/after provider callbacks; worker termination is a process-boundary fallback, followed by commit reconciliation because termination may race with a Delta commit.

## Smallest required upstream change

Before BrickHouse can support a concurrent in-process service with external providers, Sparkless needs a supported explicit session activation/ownership boundary that does not require moving an `unsendable` Python object across threads, plus documented behavior for the session active stack. Separately, the integration slice already identified by B003.2 needs session-scoped relation resolution, one delegated write path into BrickHouse's mutation service, typed Arrow batch import/export preserving decimal metadata, structured provider errors/capabilities, and a cooperative cancellation point. These are upstream tasks, not APIs that currently exist.

The safe BrickHouse 0.1 implementation may keep each Sparkless session confined to a fresh job process and its owner thread, but this does not remove the need for explicit provider hooks or allow a release to claim concurrent in-process sessions. Do not patch the Sparkless checkout or claim this design is implementable until the upstream work has tests against the exact supported client/profile.

## Result

Same-thread session isolation: **passed** for config and temp views. Cross-thread session transfer: **unsupported at the inspected revision** (reproduced PyO3 panic). Callback ownership/GIL/lock/error/cancellation contract: **specified as constraints; live callback delivery remains blocked by missing upstream hooks**.
