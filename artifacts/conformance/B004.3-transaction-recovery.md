# B004.3 — Mutation provider and recovery evidence

Date: 2026-10-19

## Environment

- macOS arm64, CPython 3.11.14
- `deltalake==1.2.1`, PyArrow 23.0.1
- Published `sparkless==4.13.4` wheel, SHA-256 recorded in [B004.2](B004.2-typed-interoperability.md)
- All tables and SQLite metadata were created under a temporary local directory; no Databricks account or remote storage was used.

The named probe is `artifacts/probes/B004.3-transaction-recovery.py`.

## Observations

The Delta table API exposes `CommitProperties(app_transactions=[Transaction(app_id, version)])`, `DeltaTable.transaction_version(app_id)`, commit metadata, and transaction history. The probe selected the default protocol written by delta-rs 1.2.1: minimum reader version 1, minimum writer version 2, no reader/writer feature lists.

The process-level recovery case creates an operation journal row in `COMMITTING`, appends one row with a table-scoped transaction ID and version 0, and signals the parent after the Delta call returns. The parent sends SIGKILL before SQLite finalization. On restart, a new DeltaTable observes transaction version 0 and commit history maps the operation metadata to Delta version 1. The journal can be finalized as committed. A guarded retry that checks the transaction version before dispatch adds no row. A classic checkpoint preserves the transaction version, and Sparkless 4.13.4 reads the checkpointed table as `[0, 101]`.

A separate fixture repeats the exact `write_deltalake` append with the same `app_id` and `version`. The provider writes another Delta commit and duplicates the row. `app_transactions` records identity; it does not itself suppress an application retry. BrickHouse must perform the lookup and skip a confirmed transaction before calling the mutation API again.

The Delta protocol documentation says checkpoints preserve transaction identifiers but not commit provenance (`commitInfo`). Custom commit metadata is useful for locating the exact Delta version while its JSON history entry remains available; it is not the durable identity source. See the [Delta-rs 1.2.1 transaction API](https://delta-io.github.io/delta-rs/1.2.1/api/transaction/), [Delta-rs 1.2.1 table API](https://delta-io.github.io/delta-rs/1.2.1/api/delta_table/), and [Delta transaction protocol](https://github.com/delta-io/delta/blob/master/PROTOCOL.md).

## Provider and recovery decision

Select Python `deltalake==1.2.1` as the single phase 0.1 mutation provider. Sparkless remains the default DataFrame/SQL semantics and reader; all writes to registered BrickHouse tables must go through the table service and this provider. This selection records the implementation boundary for B008; the package is not yet integrated into BrickHouse.

Assign a stable application ID to each table and monotonically increasing transaction versions from its serialized operation journal. Persist the operation ID, payload/options fingerprint, application ID, expected transaction version, and state before dispatch. Put both the `SetTransaction` action and operation ID metadata in the same Delta commit. Finalize the exact Delta version in SQLite before another BrickHouse write to that table can proceed.

After an operation reaches `COMMITTING`, a matching observed transaction version plus the same journal fingerprint confirms that the Delta commit occurred. Resolve its exact Delta table version from retained history using the operation metadata; only then finalize the journal as committed. If the provider cannot confirm the expected identity, the observed version is inconsistent, the application transaction has expired, the matching history entry is gone, or the operation fingerprint/journal is unavailable, retain an **uncertain** result and block automatic retries. Never infer “not committed” from a missing history row. An operator or explicit reconciliation workflow must resolve uncertainty.

Delta transaction retention can expire `SetTransaction` identifiers when `delta.setTransactionRetentionDuration` is configured. The operation-recovery horizon must fit within that retention period; otherwise a delayed restart can only produce an uncertain outcome. Current evidence covers the default local table setting, not a configured expiration window.

## Limits

Evidence covers local, unpartitioned tables with protocol reader 1/writer 2 and no table features. Sparkless 4.13.4 read the transaction-bearing checkpointed snapshot. Cloud/object storage atomicity, concurrent non-BrickHouse writers, partitions, schema evolution, deletion vectors, column mapping, timestamp variants, V2 checkpoints, transaction-retention expiry, crash during the native commit itself, and power-loss durability remain unverified. Do not advertise general Delta protocol support or exactly-once writes from this probe.
