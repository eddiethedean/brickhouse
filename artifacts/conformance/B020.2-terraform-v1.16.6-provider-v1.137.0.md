# B020.2 — Terraform Core 1.16.6 and Databricks provider 1.137.0

**Date:** 2026-10-20\
**Scope:** Local conformance for the selected workspace-file and Python-job resource subset.

## Pinned artifacts

- Terraform Core `1.16.6`, official macOS arm64 release ZIP SHA-256: `85e1bc78ab45bdc5f82a7bac3929e37d072834a584d22583a2498dc67bb624cd`. The extracted binary reported `Terraform v1.16.6 on darwin_arm64`.
- `databricks/databricks` provider `1.137.0`, official release commit `133b0ce`. The selected provider checksum lockfile is checked in at [the integration fixture lockfile](../../tests/fixtures/terraform/1.137.0/.terraform.lock.hcl).

## Implemented local profile

Terraform creates one `databricks_workspace_file` and one single-task `databricks_job` using an existing local classic cluster. The source is a real Python file in the BrickHouse workspace. The job reads its file and settings from the local API, updates by appending an immutable job-definition revision, and keeps a stable Terraform job ID. Destroy tombstones the Terraform identity and removes the workspace file while retaining immutable job and run history.

The provider needs a numeric workspace ID for its workspace-scoped resources. BrickHouse serves `/.well-known/databricks-config` with a deterministic numeric identity derived from the local workspace UUID. The capability registry labels it `simulated_local_identity`; it is neither the BrickHouse workspace UUID nor a Databricks account/workspace ID, and it provides no authentication. The provider's cluster ID refers to simulated local cluster metadata; no VM or cloud compute was started.

## Conformance evidence

The opt-in integration test uses a temporary workspace, an isolated Terraform home and state directory, a loopback host, the pinned provider cache, and the synthetic token `brickhouse-local-test-token`. It validates the config; applies and reads both resources; runs refresh-only and obtains a no-drift plan; updates uploaded Python source and task parameters; rejects an update to a missing local cluster without changing the active job revision; refreshes Terraform state back to the persisted settings; executes the updated job in a real local child process and checks its output; destroys both resources; and verifies the job/file routes return not found.

The pinned integration plus unit route checks passed:

## Limits

- This evidence applies only to Terraform Core 1.16.6, provider 1.137.0, one workspace-file resource, and one single-task Python job on an existing local classic cluster.
- The HTTP API does not authenticate callers. The synthetic provider token is not a real credential and no `.env`, `DATABRICKS_TOKEN`, GitHub secret, Databricks host, or personal account was used.
- Compute identity and lifecycle metadata are simulated. Terraform cluster/warehouse resources, new-cluster job settings, bundles, multi-task Terraform jobs, remote workspace behavior, SQL, and authentication remain unverified.
