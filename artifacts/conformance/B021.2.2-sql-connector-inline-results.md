## Released connector profiles

The local TLS integration uses the hash-verified Python 3.11 distributions from B045: `databricks-sql-connector==4.6.0` (SHA-256 `9f2128592052d3aadb7a3c46df0a8ef414402ec6ea7a0fdb8490da737fe43cdc`), `databricks-sql-kernel==1.1.0` (SHA-256 `8d7bf7aa002dc2f4864170f1e9185ba10fdf5460efb114269ec9337b084bd501`), and `pyarrow==23.0.1`.

One released connector profile exercises two observed request paths against an ephemeral BrickHouse workspace over verified loopback HTTPS. The kernel-backed connection creates and closes a session using `execution_mode=FAST`, then the Python SEA backend (`use_sea=True`, inline JSON results, compression disabled) opens its own session and submits the query. Both use the same synthetic bearer value; the child environment explicitly excludes `DATABRICKS_TOKEN` and `DATABRICKS_HOST`.

The SEA statement request carried `warehouse_id`, the returned `session_id`, `statement="SELECT :value AS answer"`, one native parameter `{name: "value", type: "INT", value: "42"}`, `disposition="INLINE"`, `format="JSON_ARRAY"`, `wait_timeout="10s"`, and `on_wait_timeout="CONTINUE"`. BrickHouse returned a successful inline result. The connector reported description `[('answer', 'int', ...)]` and fetched `[[42]]`. It then sent `DELETE /api/2.0/sql/statements/{id}` with the statement ID in the body, followed by session deletion. Each response was HTTP 200.

The loopback observer stores only synthetic request values and redacts the generated session and statement IDs from paths. It verifies strict TLS, the synthetic Bearer header, request/session identity, parameter serialization, schema, fetched values, and cleanup order. The integration does not contact the owner's Databricks account.

## BrickHouse contract and limits

The Statement Execution API now validates an optional `session_id` against the request warehouse and uses that live session's catalog/schema when the request omits them. Session creation defaults omitted `execution_mode` to `FAST` for the released SEA client; the kernel's explicit `FAST` request remains supported. Unknown sessions return 404, and cross-warehouse session use returns 400.

Terminal statement DELETE releases persisted result chunks and manifests while retaining statement history; a subsequent GET reports `CLOSED`. Repeated result closure is idempotent. Closing while a statement is pending/running returns a conflict. The existing pinned-SDK regressions continue to enforce the local `INLINE`/`JSON_ARRAY` profile and row/byte result bounds. Formats such as `ARROW_STREAM`, `CSV`, and external-link dispositions fail explicitly; no external result link is fabricated.

The kernel-backed connector's default query request is outside this slice: it sends `INLINE_OR_EXTERNAL_LINKS`, `ARROW_STREAM`, and `LZ4_FRAME`, which the local profile explicitly rejects at the disposition validation step. Kernel session open/close passes, and SEA-mode query/result behavior passes, but this does not establish kernel Arrow-stream compatibility, Thrift compatibility, remote Databricks behavior, or full DB-API metadata support. B021.2.3 covers connector-visible SQL errors, cancellation where advertised, retention and additional methods.
