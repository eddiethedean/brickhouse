# B013.3 — Worker supervision and durable attempt outcomes

Date: **2026-10-20**. Task: **done**. Decision: [ADR 0020](../../docs/decisions/0020-worker-supervision-and-outcomes.md).

## Behavior

The internal Python worker runner now supports finite timeouts, cooperative cancellation requests, bounded SIGTERM grace, POSIX process-group escalation to SIGKILL, and reaping of the directly owned process. It always drains both bounded output streams, revokes credentials scoped to the attempt, redacts the bearer and truncated suffixes from captured output, and invokes caller-supplied staging cleanup after the worker stops. Cleanup failures record only their exception type.

Workspace metadata schema 5 adds a journal keyed by run and attempt. It records `running` before process start, then the observed exit code, completion/timeout/cancellation state, resolved interpreter/script/working directory, bounded byte counts, truncation flags, timestamps, and cleanup status. Launch failures do not invent an exit code. The journal stores neither worker logs nor credentials. Migrations from schema 3 through the current schema are covered.

Fresh interpreters do not inherit caller credentials, import paths, environment mutations or module state. A two-attempt real-process check verifies that each attempt gets its own immutable context and starts without prior attempt environment or `sys.modules` changes. This is process isolation, not a hostile-code sandbox. Process-group descendant cleanup is supported and tested on POSIX; Windows direct-child termination does not claim descendant cleanup.

## Limits

B013 provides internal supervision and one local attempt-outcome table only. There is no worker listener, public job/run API, durable user log/output retrieval, retry policy, active-run restart reconciliation, or Windows descendant-group guarantee. B014 owns job/run lifecycle composition.
