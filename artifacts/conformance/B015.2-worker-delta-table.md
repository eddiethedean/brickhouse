# B015.2 — Worker DeltaTable compatibility subset

Date: **2026-10-21** (America/New_York). Result: **passed for the selected read-only local worker profile**.

## Selected behavior

Managed workers expose only `delta.tables.DeltaTable`, backed by BrickHouse's worker facade. The parent process and unrelated worker processes retain their own `delta` modules. If the worker interpreter has a conflicting `delta-spark` package or preloaded Delta namespace, the worker rejects it instead of replacing it.

The selected factories are `forName`, `forPath`, and `isDeltaTable`. They query the attempt-authenticated parent service and accept only registered BrickHouse Delta table identities and canonical local paths. `forName` does not accept temporary views; `forPath` rejects a real but unregistered Delta directory; `isDeltaTable` reports registration. `toDF` and `alias` read through the existing worker Sparkless session and external-catalog provider.

`delete`, `update`, `merge`, `restoreToVersion`, `restoreToTimestamp`, and `vacuum` raise `UnsupportedWorkerDeltaOperationError`. DataFrame and SQL writes remain blocked too, so this facade does not bypass the shared table mutation service. Delta Lake JVM behavior, arbitrary paths, and other `delta` modules remain unsupported.

## Sparkless issue review

Sparkless 4.14.1's public external-catalog API is sufficient for the selected read facade. No new Sparkless change was required by B015. The already-open [#1705](https://github.com/eddiethedean/robin-sparkless/issues/1705) covers cooperative active SQL/DataFrame cancellation, and [#1706](https://github.com/eddiethedean/robin-sparkless/issues/1706) covers bounded Arrow batch/stream export. The later broader callback review filed [#1707](https://github.com/eddiethedean/robin-sparkless/issues/1707) for preserving structured provider error categories; that follow-up is not needed by this read-only worker API.
