# B048.1 — Diagnostics server bind boundary

**Result:** passed · **Scope:** local IPv4 loopback bind enforcement only · **Date:** 2026-10-21

## Finding and resolution

The `brickhouse serve` CLI already rejected a non-loopback host, but callers of `create_diagnostic_server(context, host, port)` could bind the same unauthenticated API to a public interface. `serve_diagnostics()` also accepted a non-loopback address when called directly. This bypass violated the existing loopback-only local-server contract.

`require_ipv4_loopback_host()` now accepts only numeric IPv4 loopback addresses. The direct server factory calls it before constructing API services or opening a socket; the direct serve function calls it before signal setup; and the CLI reuses it before acquiring a workspace context. IPv6, hostnames (including `localhost`), and non-loopback IPv4 are rejected. An IPv4 loopback bind remains supported. See [`diagnostic_server.py`](../../src/brickhouse/diagnostic_server.py#L27) and [`cli.py`](../../src/brickhouse/cli.py#L111).

## Evidence

- The new tests cover invalid IPv4, IPv6, and hostname inputs at the direct factory, direct serve rejection before signal setup, and a successful loopback bind: [`test_diagnostic_server.py`](../../tests/unit/test_diagnostic_server.py#L21).
- Existing CLI coverage confirms rejection before workspace acquisition: [`test_cli.py`](../../tests/unit/test_cli.py#L156).
- Ruff check and format passed for the four changed Python files; strict mypy passed for all 70 source files; `git diff --check` passed.

## Boundary

This prevents accidental network exposure by these server entry points. It does not authenticate local callers, make compatibility SDK tokens an authorization mechanism, authorize one local user against another, or sandbox Python workers. The server remains intended for one trusted local operator on a tested POSIX filesystem.
