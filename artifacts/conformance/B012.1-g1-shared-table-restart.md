# B012.1 — G1 shared table reads through service restart

Date: 2026-10-21

## Local conformance

The regression creates a workspace, starts a local loopback SDK service, and
writes a typed managed Delta table through a fresh `SparklessSessionFactory`
session. The write commits Delta version 0. The pinned Databricks SDK then
executes a real SQL statement over that registered table. The test compares the
SDK result schema and rows with the Arrow input, reads the same table from a
separate fresh Sparkless session, shuts down the HTTP service and workspace
context, and reopens both over the same workspace directory.

After restart, the test verifies the original table ID and canonical location,
fetches the earlier persisted SQL statement result, submits the query again,
and reads the table through another fresh Sparkless session and the native
Delta service. Row values, schema, and Delta version remain unchanged.

The focused command was:

```sh
env -u DATABRICKS_TOKEN -u DATABRICKS_HOST PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 \
  PYTHONPATH=src /tmp/brickhouse-b0171-env/bin/python -m pytest -q \
  tests/integration/test_g1_shared_table_restart.py
```

It passed **1 test** with Python 3.11.14, `sparkless==4.15.0`,
`databricks-sdk==0.153.0` against loopback only, `deltalake==1.2.1`,
`pyarrow==23.0.1`, SQLite 3.53.4, and workspace metadata schema 17. Ruff check
and format check passed for the integration test. Databricks credential
variables were unset. The SDK used a synthetic local token; no real workspace,
cloud compute, Java, full PySpark, Docker, or remote execution was involved.

This proves the selected local G1 shared-table and graceful service-restart
path only. It does not establish crash recovery, the full Java/network
independence gate, all edge cases in B012.2, or Databricks runtime parity.
