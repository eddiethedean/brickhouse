# B014.3.3 — Active job restart recovery

**Date:** 2026-10-20\
**Status:** complete for local Python job attempts\
**Client:** `databricks-sdk==0.153.0` against local loopback only\
**Metadata:** schema 9; prior output remains immutable

## Implemented behavior

- Worker outcome records now retain the launched child PID. Schema 9 adds this field and allows a worker outcome to be marked interrupted without inventing an exit code; schemas 1–8 migrate transactionally.
- The job service reconciles active persisted runs at startup and again when callers poll. If a worker still exists, the service leaves its run active and does not replay it. Once the process is gone, the service preserves observed terminal attempts, marks an unobserved in-flight attempt and run interrupted, and retains `WORKSPACE_RESTARTED` as the state message.
- The interrupted SDK result maps to `INTERNAL_ERROR`. Pending tasks remain unexecuted. Idempotency replay returns the existing interrupted run and does not create another run.
- SDK output retrieval selects the latest attempt with persisted output, so output from a completed earlier retry stays available when a later retry is interrupted before capture.

## Verification

A POSIX restart integration starts the actual loopback job service in a child process, runs a Python script that fails once and starts a retry, kills the service and worker, then reopens the workspace and queries it with the pinned SDK. The run and second attempt are interrupted with no exit code, the first attempt's observed exit and output remain available, idempotency replay returns the same run, and the script's side-effect counter remains at two. A schema 8 fixture migrates to schema 9 and its running worker outcome can be interrupted without an exit code.

## Limits

A child process that survives service restart is not adopted or killed; the service leaves the run active until later polling sees that PID disappear. Side effects can therefore continue after the server has stopped. This does not provide cross-host supervision, process identity protection against PID reuse, exactly-once execution, or replay of undispatched tasks. No `.env`, Databricks account, cloud compute, Spark, or JVM was used.
