# B019.2.1 — SQL UPDATE and DELETE

Date: 2026-10-21  
Result: **passed locally** for the selected predicate/assignment subset.

## Environment

- Python 3.11.14
- Sparkless 4.15.0
- `deltalake==1.2.1`
- PyArrow 23.0.1
- SQLGlot 30.24.0
- Databricks SDK 0.153.0
- SQLite 3.53.4; workspace metadata schema 18

## Implemented behavior

SQL UPDATE and DELETE now bind one registered Delta table and a required WHERE predicate, validate simple column/literal expressions against the current Arrow schema, then call delta-rs `DeltaTable.update()` or `DeltaTable.delete()`. These native provider operations receive the per-table application transaction and BrickHouse operation/fingerprint metadata; there is no read/overwrite mutation path and BrickHouse never edits `_delta_log`.

The workspace journal records exact affected-row counts from Delta history and binds each committed operation to one snapshot version. A successful zero-row operation is stored as `no_op` without consuming a Delta transaction version because delta-rs does not create a commit for that case. A provider rejection is terminally recorded as `failed` only when the table version and application transaction are confirmed unchanged. Unreconciled outcomes remain uncertain and block later writes. Metadata schema 18 migrates and preserves schema-17 operation records.

The local SQL reader sees the updated/deleted rows through a fresh Sparkless 4.15.0 session, with the original Arrow schema preserved. The pinned SDK Statement Execution endpoint also completes an UPDATE and a following SELECT reads the committed value.

## Evidence

- `tests/unit/test_sql_mutations.py`: selected UPDATE arithmetic/literals, DELETE with `IS NULL`, exact schema and affected rows, provider history metadata, Sparkless-visible results, zero-row no-op replay, transaction sequencing, unsupported/missing columns and predicates, type rejection without side effects, stale-snapshot rejection, and history-based recovery after an injected journal-finalization failure.
- `tests/unit/test_sql_statement_api.py::test_sdk_statement_update_commits_and_a_followup_statement_reads_it`: real pinned SDK over loopback.
- `tests/unit/test_delta_operation_journal.py::test_metadata_schema_17_operation_records_migrate_through_schema_19`: committed operation preservation through the schema-17 to schema-18 migration and the subsequent schema-19 journal rebuild.
- The combined focused regression run covered the mutation, SQL service/API, Delta service/journal, workspace migration, catalog, and job repository suites.

The focused local suites were run with `DATABRICKS_TOKEN`, `DATABRICKS_HOST`, and `DATABRICKS_PROFILE` unset. No Databricks workspace or cloud compute was contacted.

## Limits

Only one table, unqualified columns, a required WHERE clause, and simple column/literal arithmetic, comparisons, boolean predicates, `IS NULL`, and literal-list `IN` predicates are accepted. UPDATE aliases, joins/FROM, DELETE USING, subqueries, functions, RETURNING, ORDER/LIMIT, and column-qualified expressions reject before provider dispatch. MERGE, SQL DESCRIBE/HISTORY, and VERSION AS OF remain B019.2.2–B019.2.4; this evidence does not claim broader Spark or Databricks SQL parity.
