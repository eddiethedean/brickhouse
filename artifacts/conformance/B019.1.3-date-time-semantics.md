# B019.1.3 — Date, timestamp, and timezone semantics

**Status:** passed locally on 2026-10-21  
**Scope:** DATE/TIMESTAMP projection, literals, date predicates, UTC normalization and boundary comparisons, null propagation, and invalid conversion cases using the versioned orders Delta fixture. The initial capture used Sparkless 4.15.0; the 2026-10-22 addendum records requalification with the published 4.15.1 wheel. Local profile: `spark35-local-v1`; session timezone UTC.

## Local observations

[The fixture](../../tests/fixtures/sql/B019.1.3-date-time-cases.json) composes the real local Delta input from [B019.1.1](../../tests/fixtures/sql/B019.1.1-orders-scalar-query.json). The SQL result for `event_date` is Arrow `date32`; filtering against `DATE '2026-10-17'` returns true for order 2 and preserves null for order 3. SQL date and timestamp literals return `date32` and naive Arrow `timestamp[us]` respectively.

The input's `event_ts` field is Arrow `timestamp[us, tz=UTC]`. Sparkless SQL projection returns `timestamp[us]` without timezone metadata, but the stored offsets are normalized to UTC values: the input `2026-10-17T23:30:00-04:00` appears as `2026-10-18T03:30:00`. The fixture records both source and output types. In an explicit `CAST(event_ts AS TIMESTAMP)` comparison at that exact boundary, `>=` is true and `<` is false. Invalid DATE and TIMESTAMP strings raise `ValueError` and are retained with their message categories.

An unadapted comparison between the timezone-aware source column and a timestamp literal raises `SparklessError` because the evaluated series have Polars types `Datetime('μs', 'UTC')` and `Datetime('μs')`. The test asserts the error and does not hide it with an automatic cast. This missing timezone coercion was reported as [Sparkless issue #1714](https://github.com/eddiethedean/robin-sparkless/issues/1714).
