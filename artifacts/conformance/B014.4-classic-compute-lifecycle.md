# B014.4 — Classic compute identity and lifecycle

- Date: 2026-10-20
- Status: completed resource-metadata slice
- Scope: pinned SDK all-purpose cluster lifecycle plus internal new/shared job-compute consumers
- Decision: [ADR 0023](../../docs/decisions/0023-local-classic-compute-lifecycle.md)

## Implemented

Metadata schema 7 adds one durable compute identity for each all-purpose cluster and each `(job run, compute key)` job resource. New/shared job resources persist their complete planned consumer set before dispatch. Consumers register, start, and release through `WorkspaceContext.compute`. New/shared resources activate on the first consumer and terminate after the last planned consumer releases. All-purpose IDs survive termination and can autostart when a registered consumer explicitly requests it. An injected UTC clock drives idle termination.

State changes append immutable events. A monotonically increasing generation fences stale sessions after start, edit, restart, and termination. SQLite constraints/triggers enforce identity immutability, legal state changes, monotonic generations, consumer transitions, and append-only event history. Permanent deletion hides an all-purpose cluster from API reads while retaining its identity and history.

The loopback API supports the pinned Databricks SDK 0.153.0 cluster create/get/list/edit/start/restart/delete/permanent-delete routes. `delete` is SDK's terminate operation. API state messages explicitly say allocation is simulated. Runtime/access validation resolves only the local alias `spark35-local-v1` with the selected standard and dedicated local profiles. Unknown runtime/access mappings, Photon, JVM options, cluster policies, cloud-specific settings, credential-shaped configuration keys, and other unsupported effects fail explicitly.

## Verification

The SDK tests use a synthetic local token and temporary SQLite workspace. They exercise create/get/list pagination/edit/restart/terminate/start/permanent-delete, SDK result parsing, missing resources, unsupported runtime/access/Photon requests, and identity persistence after workspace reopen. Service tests use real job/task metadata, SQLite triggers, two planned shared consumers, a controlled clock, idle termination, explicit autostart, generation changes, and durable invalidation events.

All checks use local files and a loopback server. No `.env` was loaded, no Databricks account was contacted, and no Spark/JVM/cloud compute was started.

## Limits

- `spark35-local-v1` is a BrickHouse-local alias, not a Databricks Runtime string or a claim of Sparkless parity.
- Standard/dedicated labels do not enforce user isolation, permissions, or a malicious-code sandbox.
- Node types/counts and all allocation/timing are simulated; lifecycle records do not establish successful worker execution.
- Worker/session cancellation, run-to-worker context, public job routes, and behavior when restarting compute under active work remain B014.5/B014.6 scope.
- No classic runtime/access behavior was observed on the owner's account; the local SDK profile is not Databricks workspace compatibility evidence.
