# B005.4 — Local credential isolation

Date: **2026-10-16**.

## Evidence

`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q tests/unit/test_capture_isolation.py` passed **5 tests**. The tests use a temporary `.env` and `.databrickscfg` containing sentinel credentials, a `.invalid` workspace host, and a subprocess hook that fails if the ordinary BrickHouse CLI reads either credential file or opens any socket. `brickhouse --version` succeeded with inherited `DATABRICKS_TOKEN`, `DATABRICKS_HOST`, and `DATABRICKS_CONFIG_PROFILE` present, without reading profile files or opening a network connection.

The sanitized SQL fixture loads after all Databricks credential/configuration variables are removed. The named capture probe requires an explicit HTTPS `--host`, reads only `DATABRICKS_TOKEN` from the process environment or the explicitly allowed `.env`, and fails with a sanitized `token_missing` status before making a request when no token is available. Tests also verify process-environment token precedence over a temporary `.env` value.

## Scope and limits

The current BrickHouse package has no SDK, CLI, or HTTP API client implementation beyond the local help/version CLI. These checks prove that present import/CLI/fixture paths do not discover credentials or contact a workspace; they do not substitute for host/auth isolation tests for future Databricks SDK, CLI, Terraform, or SQL connector integrations. Each future local client test must inject a loopback host and local compatibility token, block external hosts, and run with personal profiles inaccessible.
