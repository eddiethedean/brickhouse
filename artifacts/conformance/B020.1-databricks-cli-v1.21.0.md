# B020.1 — Databricks CLI v1.21.0 local workflow

**Date:** 2026-10-20\
**Status:** complete for the selected workspace source-import and Python job workflow\
**Client:** Databricks CLI `v1.21.0`, commit `71934db`\
**Binary:** macOS arm64 release ZIP, SHA-256 `5c899a18bb280a33cb1814418fd1352a6a6e5487a2d9eb850c573114885c2f83`

## Result

The versioned CLI fixture in [`test_databricks_cli_v1_21_0.py`](../../tests/integration/test_databricks_cli_v1_21_0.py) runs the actual Go CLI against an ephemeral BrickHouse HTTP server bound to `127.0.0.1`. It verifies:

- `workspace import --file` imports Python source to a temporary `/Workspace/Shared` path.
- Reimport without overwrite returns an error for the existing workspace file.
- `jobs create` rejects a Python task whose workspace source is missing.
- A valid job can be created, submitted with `jobs run-now`, polled with `jobs get-run`, and read with `jobs get-run-output`; the local worker's actual output is returned.
- The isolated workspace directory is deleted after server shutdown and context release.

The CLI was downloaded from the official [`v1.21.0` release](https://github.com/databricks/cli/releases/tag/v1.21.0). Its published macOS arm64 ZIP hash matched the value above, and `databricks version` returned `Databricks CLI v1.21.0`. The fixture supplies a synthetic local token and an empty temporary CLI config. The HTTP API does not authenticate this token; this case establishes wire/workflow behavior only, not auth compatibility. Databricks host metadata discovery against the loopback host is unsupported and the CLI proceeds after its local lookup fails.

## Limits

This is a partial client workflow. The CLI's broad workspace API, catalogs, SQL, compute resources, serverless/classic profiles, bundle lifecycle, Terraform resources, CLI authentication, cloud identity, and remote Databricks compatibility are not established. `DATABRICKS_CLI` is optional in ordinary test runs; set it to the pinned binary to execute this integration fixture.
