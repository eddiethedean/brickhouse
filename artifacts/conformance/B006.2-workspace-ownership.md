# B006.2 — Workspace ownership and migration evidence

Date: 2026-10-19

## Result

Added a cross-process POSIX advisory lock at `.brickhouse-owner.lock`. `acquire_workspace_owner()` validates a workspace before taking a nonblocking exclusive `flock`, writes a mode-0600 diagnostic record, and returns a context-managed handle. A competing process receives `WorkspaceInUseError`. Orderly shutdown clears the diagnostic contents before unlocking. If an owner process dies, the kernel releases its lock; the next process reacquires it and can identify the previous record without trusting the stored PID for liveness.

SQLite initialization now goes through an ordered migration runner. `BEGIN IMMEDIATE`, migration DDL, history insertion, and `PRAGMA user_version` are one transaction. A failed step rolls back all of them. Unsupported sequence gaps and inconsistent version/history state are rejected. Version 1 is the only migration currently present.

Each workspace has a separate owner lock and `metadata.sqlite`. The test uses two real workspace directories and distinct persisted metadata values while both owner locks are held.

## Scope limits

This provides a lock primitive, not automatic server ownership; B006.3 must use it during service startup and shutdown. Locking is tested on the local POSIX filesystem only. Windows and network filesystem behavior are not claimed. The migration runner can apply ordered future migrations, but only schema version 1 exists and no older released workspace upgrade is promised.
